# Архитектура Apix

Apix — нативный API-клиент, написанный на Rust. Интерфейс рисуется на GPU с
помощью [GPUI](https://github.com/zed-industries/zed) (движка интерфейса Zed) и
библиотеки компонентов [gpui-kit](https://github.com/longbridge/gpui-kit). В
нём нет ни WebView, ни Electron.

## Принципы

1. **Локально прежде всего, дружелюбно к git.** Коллекция — это папка с
   небольшими файлами TOML. Нет ни учётной записи, ни обязательного облака.
   Коллекции коммитят, сравнивают и проверяют на ревью, как код.
2. **Интерфейс никогда не блокируется.** Сеть, диск, разбор и скрипты работают
   вне потока интерфейса. Поток интерфейса только раскладывает и рисует.
3. **Один движок, много интерфейсов.** Настольное приложение, CLI `apix` и
   будущие интерфейсы (TUI, сервер MCP) используют одни и те же crates, поэтому
   запрос ведёт себя одинаково везде, в том числе в CI.
4. **Масштабирование до огромных ответов.** Ответ JSON размером 100 MB должен
   прокручиваться плавно. Раскладываются только видимые строки (виртуальные
   списки), а тело разбирается лениво.
5. **Лёгкий и быстро запускается.** Скорость и возможности важнее размера.
   Release-бинарник остаётся меньше 100 MB (сегодня 54.4 MB; приложения на
   Electron весят 300 MB+) и открывает окно меньше чем за 150 ms.

### Один настольный crate для трёх операционных систем

GPUI и gpui-kit работают в Windows, macOS и Linux из одного и того же кода —
так выпускается и Zed. Поэтому отдельных папок интерфейса для каждой ОС нет.
Код, который действительно различается между ОС, находится за `cfg` в
`crates/apix-desktop/src/platform/{windows,macos,linux}.rs`: заголовок окна и
кнопки управления окном, размытие/vibrancy, строка меню macOS, связь файлов
`.apix` с приложением и доступ к связке ключей. Установщики и иконки лежат в
`packaging/{windows,macos,linux}/`. Отдельный интерфейс выделили бы, только если
какой-то ОС когда-нибудь понадобится действительно другой интерфейс.

Направление зависимостей: `core` ← `http`/`script`/`proto` ← `cli`/`desktop`.
От `desktop` ничего не зависит.

## Поток данных запроса

```
.apix file ──load──▶ Request ──resolve(Variables)──▶ Request (resolved)
                                                        │
                       pre-request script (later) ◀─────┤
                                                        ▼
                                         apix-http::HttpClient::send
                                                        │  (tokio runtime, background thread)
                                                        ▼
                    Response {status, headers, body: Bytes, timing}
                                                        │
                           test script (later) ◀────────┤
                                                        ▼
                         UI: status line, virtualized body viewer
```

`{{variables}}` разрешаются слоями. Более поздние слои важнее:
**глобальные → коллекция (`apix.toml`) → окружение → переопределения (CLI `--env-file`, `APIX_VAR_*` и `--var`, сопоставляемые с именами коллекции без учёта регистра; скрипт `pm.variables.set`)**.
Неопределённые имена остаются на месте и о них сообщается, поэтому интерфейс
может их подчеркнуть, а CLI — отказаться отправлять запрос.

### Сетевая трассировка

Каждая отправка создаёт свой собственный короткоживущий клиент reqwest, поэтому
всё, что он записывает, относится к этому запросу (`apix_http::trace`).
Резолвер замеряет DNS, слой Tower вокруг коннектора reqwest замеряет каждое
соединение, а политика перенаправлений отмечает каждый переход. reqwest не
отдаёт своё TLS-соединение и не позволяет собственному коннектору вернуть его,
поэтому подробности TLS берутся изнутри rustls, через конфигурацию клиента,
которую Apix строит сам (`use_preconfigured_tls`, `tls::traced_config`, хуки в
`tls_trace.rs`):

- оборачивающий проверяющий сертификатов записывает цепочку, которую прислал
  сервер, и подпись какой версии он проверяет (TLS 1.2 или 1.3), затем
  позволяет решить обычному проверяющему (или «принимать всё» при выключенных
  проверках);
- у хранилища сеансов, которое ничего не хранит, запрашивается подсказка для
  обмена ключами, пока пишется client hello, — это отмечает начало рукопожатия
  TLS: время соединения до этого момента (после DNS) — это TCP, после — TLS;
  ему же сообщается группа, выбранная сервером (TLS 1.3);
- наборы шифров — собственные наборы rustls, созданные один раз с тонкой
  обёрткой вокруг их шифрования, которая отмечает, какой набор был выбран.
  Наборы `'static` и общие, поэтому обёртка находит запрос через
  thread-local-значение, заданное на время опроса future запроса (`Scoped`);
  рукопожатие выполняется внутри этого опроса.

ALPN следует из версии ответа (HTTP/2 поверх TLS только после согласования
`h2`). Сжатые тела распаковывает Apix (`decode.rs`, gzip, zlib или raw deflate,
brotli, по мере поступления), а не reqwest, который отбросил бы
`Content-Encoding` и размер при передаче.

## Формат на диске

```
my-api/
├── apix.toml               имя + [vars] и [auth] уровня коллекции
├── environments/
│   ├── dev.toml            [vars] base_url = "http://localhost:8080"
│   └── prod.toml
├── users/
│   ├── folder.toml         необязательно: [auth] для запросов этой папки
│   ├── list-users.apix
│   └── create-user.apix
└── health.apix
```

**Наследование авторизации.** Запрос без `auth` наследует её от ближайшей
папки, в `folder.toml` которой она задана, затем от коллекции (`apix.toml`),
затем от проекта (`apix-project.toml`); если её нигде нет, ничего не
отправляется. `auth = "none"` в запросе (или папке) останавливает наследование.
`apix_core::project::inherited_auth` выполняет этот поиск одинаково для
настольного приложения, CLI и «Копировать как».

**Настройки запроса.** Таблица `[settings]` (тайм-аут, перенаправления,
проверка TLS, прокси, клиентский сертификат, доверенный CA, cookie) находится на
тех же четырёх уровнях. Каждое поле — `Option`: `None` наследуется
по каждому полю через ту же цепочку (`apix_core::project::inherited_settings`),
а то, что всё ещё не задано, берётся из значений по умолчанию в
`RequestSettings::effective` — без тайм-аута, следовать максимум 10
перенаправлениям, проверять TLS, прокси из окружения, cookie включены. Движок
применяет результат, когда строит `reqwest::Client` для каждой отправки (файл
доверенного CA добавляет свои сертификаты как корневые); общее хранилище cookie
(`cookie_store`, который менеджер cookie может показывать и редактировать)
передаётся этому клиенту, если запрос не выключает cookie.

**Подписанная авторизация.** AWS Signature V4, OAuth 1.0a и Digest — чистые
функции в `apix_core::sign`, проверенные по набору тестов AWS, RFC 7616,
RFC 7636 и классическому примеру OAuth 1.0, поэтому движок и «Копировать как»
подписывают одинаково. Движок сначала строит `reqwest::Request`, а затем
подписывает его (хешу полезной нагрузки AWS нужно окончательное тело; поток
multipart отправляется как `UNSIGNED-PAYLOAD`). Digest отправляет запрос один
раз, читает challenge из ответа 401 и отвечает на него в том же соединении.
OAuth 2.0 находится в `apix_http::oauth2`: токен получается перед отправкой
(client credentials, password или authorization code с PKCE, где браузер
возвращается на одноразовый слушатель на 127.0.0.1), хранится в памяти для
каждого сочетания сервера, клиента, grant, scope и пользователя, обновляется
своим refresh token и никогда не записывается на диск.

Файл запроса:

```toml
name = "Create user"
method = "POST"
url = "{{base_url}}/orgs/:org/users"   # без query: она в [[query]]

[[query]]
key = "notify"
value = "yes"

[[path]]                 # значение сегмента :org
key = "org"
value = "{{org}}"

[[example]]              # ответ, хранящийся вместе с запросом
name = "Created"
status = 201
body = '{ "id": 7 }'
[example.request]        # из чего он был отправлен, в записанном виде
method = "POST"
url = "{{base_url}}/orgs/:org/users?notify=yes"

[[headers]]
key = "X-Trace"
value = "on"
enabled = false          # хранится в файле, не отправляется

[body]
json = '''
{ "name": "Ada" }
'''

[auth.bearer]
token = "{{token}}"

[[assert]]               # проверка без кода, выполняется после тестовых скриптов
target = "status"
op = "=="
value = "201"
```

**Проверки.** Строки `[[assert]]` сравнивают цель (`status`, `time`, `size`,
`body`, `body.<path>`, `header.<name>`) со значением с помощью `==`, `!=`, `>`,
`>=`, `<`, `<=`, `contains`, `not contains`, `exists`, `not exists`, `matches`
или `is` (тип JSON). `apix_script::assertions_script` превращает их в ещё один
тестовый скрипт, поэтому везде они сообщают о результатах так же, как `pm.test`.

**Тела.** `[body]` содержит одно из: `json`, `text`, `xml`, `form` (строки в
URL-кодировке), `multipart` (строки с `file = true` для файловых полей и
необязательным `content_type`), `binary = { file = "…" }` или `graphql`
(`query` и `variables`). Пути к файлам могут содержать переменные и
указываются относительно файла запроса; `Request::with_files_relative_to`
делает их абсолютными после разрешения переменных — одинаково в приложении и в
CLI. Движок читает файлы только при отправке, поэтому отсутствующий файл — это
ошибка отправки, а не ошибка загрузки. Тело GraphQL отправляется как JSON
`{"query", "variables"}`; неверные переменные останавливают отправку. При теле
multipart заголовок `Content-Type: multipart/…` без boundary движка (частый в
экспортах Postman) отбрасывается, чтобы тело оставалось читаемым.

**gRPC.** Запрос, URL которого — `grpc://host:port` (или `grpcs://` для TLS),
называет свой метод в `[grpc]`; тело JSON — это сообщение, а список JSON —
поток сообщений для метода, который принимает поток. Без `protos`
спрашивается сервер (рефлексия). Пути указываются относительно файла запроса.

```toml
name = "Say hello"
url = "grpc://localhost:50051"

[body]
json = '{"name": "Ada"}'

[grpc]
method = "helloworld.Greeter/SayHello"
protos = ["../protos/helloworld.proto"]   # необязательно
import_paths = ["../protos"]              # необязательно
```

Вместо файлов `definition` хранит описание в самом запросе: текст `.proto` или
набор дескрипторов в виде JSON. Оно важнее `protos`. `guessed = true` отмечает
описание, выведенное из типов или JSON: рефлексия сервера важнее него, и о
различиях сообщается. `protos` также принимает наборы дескрипторов, бинарные
или `.json`.

```toml
[grpc]
method = "shop.v1.Orders/Create"
guessed = true
definition = """
syntax = "proto3";
package shop.v1;
service Orders { rpc Create(CreateRequest) returns (CreateResponse); }
message CreateRequest { string customer = 1; }
message CreateResponse {}
"""
```

Открытые вопросы:
- **Секреты.** Значения окружения, такие как токены, не должны попадать в
  коммит. `environments/<name>.local.toml` накладывается поверх `<name>.toml`.
  Запись такого файла добавляет `*.local.toml` в `.gitignore` рядом с
  `environments/`, если его там нет. Секрет может хранить заполнитель в общем
  файле, чтобы участники команды видели имя. По желанию (Настройки › Секреты
  окружений) секреты вместо этого попадают в связку ключей ОС: тогда
  `<name>.local.toml` содержит только `keychain = "<id>"`, а значения хранятся
  в записи `env:<id>` службы `Apix` (`apix_vault::keychain::save_text`, с
  разбиением на несколько записей из-за ограничения Windows в 2560 байт).
  `apix_core::secrets::use_keychain` решает, куда пишутся новые секреты; чтение
  следует файлу, поэтому CLI не нужна никакая настройка. Идентификатор
  путешествует вместе с файлом, поэтому переименование окружения или
  перемещение папки сохраняет связь. Внутри зашифрованной коллекции секреты
  остаются в хранилище (vault).
- **Динамические переменные.** `{{$name}}` заполняет `apix_core::dynamic`, если
  переменная с таким именем не определена, причём каждое вхождение получает
  новое значение (`$guid`, `$timestamp`, `$isoTimestamp`, `$randomEmail`, …).
  Без лишних crates: небольшой генератор xorshift и написанный вручную
  форматировщик дат UTC.
- **Порядок в боковой панели.** Если ничего не сохранено, сначала идут папки,
  затем запросы, каждые по имени. Перетаскивание сохраняет список `order` имён
  дочерних элементов в `folder.toml` папки (или в `apix.toml` коллекции);
  `store::place` ставит один элемент перед другим или после него, а
  переименования и перемещения поддерживают список в актуальном состоянии.
  Имена, которых список не знает, идут следом в порядке по умолчанию, поэтому
  новый файл никогда не пропадает. Коллекции проекта используют `order` в
  `apix-project.toml` (`Project::place_collection`). Импортёр Postman пишет
  `order` только если порядок в Postman отличается от порядка по умолчанию.

### Проекты

Проект объединяет коллекции и владеет окружениями, общими для всех них:

```
shop/
├── apix-project.toml       имя, общие [vars], порядок коллекций, group_by, привязки, цвета
├── environments/           test.toml, prod.toml (+ секреты *.local.toml)
├── users/                  коллекция (apix.toml + файлы .apix)
└── payments/               коллекция; может быть привязана к некоторым окружениям
```

`[colors]` сопоставляет папке коллекции имя цвета (`red`, `orange`, `yellow`,
`green`, `teal`, `blue`, `purple`, `pink`); приложение рисует его точкой в
боковой панели и на вкладках. `project::move_collection_into` перемещает папку
коллекции в проект (копирование и удаление при переносе между дисками).

Слои переменных, более поздний важнее: переменные проекта → переменные
коллекции → окружение проекта → окружение коллекции с тем же именем (каждое со
своими секретами `.local.toml`). CLI (`apix run --env`) и настольное приложение
используют одну и ту же функцию, `apix_core::project::variables`.
`group_by = "environment"` раскладывает боковую панель как
Проект → Окружение → Коллекции, а `[pins]` ограничивает коллекцию некоторыми
окружениями.

### Зашифрованные коллекции (M4)

Формат и движок находятся в `crates/apix-vault`. Остальной Apix обращается к
ним через `apix_core::vfs` — тонкий слой с теми же вызовами, что и `std::fs`:
путь под корнем разблокированного хранилища обслуживается из хранилища с
расшифровкой в памяти; любой другой путь идёт на диск. Поэтому хранилище
данных, боковая панель, вкладки и CLI продолжают использовать обычные пути, и
ничего расшифрованного никогда не пишется на диск. Разблокированные хранилища
живут в общем для процесса реестре; блокировка (вручную, после 15 минут
бездействия или при выходе) отбрасывает хранилище и стирает его ключ. Удаление
внутри зашифрованной коллекции необратимо: системная корзина хранила бы
расшифрованные файлы.

```
my-api/
├── apix-vault.toml   открытый заголовок: формат, стоимость и соли Argon2id,
│                     ключ данных, обёрнутый паролем и ключом восстановления
├── .gitignore        objects/local/
└── objects/
    ├── index.apixe   настоящие пути всех файлов, зашифрованные
    ├── 3f9c…e1.apixe по одному зашифрованному файлу; случайные имена, плоско (без структуры папок)
    └── local/        секреты *.local.toml, тот же формат, никогда не коммитятся
```

- Случайный 256-битный **ключ данных** шифрует каждый файл с помощью
  XChaCha20-Poly1305 и нового nonce при каждой записи. Идентификатор объекта —
  это связанные данные, поэтому подменить или переименовать блоки незаметно
  нельзя.
- Ключ данных хранится дважды: обёрнутый ключом, выведенным из **пароля**
  (Argon2id, 64 MiB, 3 прохода), и ключом, выведенным из **ключа
  восстановления** (160 случайных бит, показывается один раз как
  `XXXX-XXXX-…` в Crockford base32). Смена пароля переобёртывает ключ; файлы
  заново не шифруются.
- Переименования и перемещения затрагивают только зашифрованный индекс.
- Разблокированный ключ живёт только в памяти (`zeroize` стирает его при
  блокировке).
- Git по-прежнему видит, какой объект изменился, но никогда — что в нём.
  Безопасность обеспечивают шифр и пароль, а не секретность формата; Apix —
  проект с открытым исходным кодом.
- Пароль можно запомнить в хранилище учётных данных ОС
  (`apix_vault::keychain`, через crate `keyring`: Credential Manager, macOS
  Keychain, Secret Service). Одна запись на хранилище под службой `Apix` с
  именем `vault:<absolute folder>` (в нижнем регистре в Windows). Это
  включается по желанию в окне разблокировки; приложение и CLI пробуют её,
  прежде чем спрашивать, пароль, который больше не открывает хранилище,
  удаляется и запрашивается снова, смена пароля обновляет запись, а
  расшифровка коллекции удаляет её. Когда хранилища нет, Apix просто
  спрашивает, как и раньше.

## Скрипты (M5)

`apix_core::scripts` находит скрипты запроса (`_collection.<event>.js`,
`_folder.<event>.js` каждой папки, затем `<request>.<event>.js`; события —
`prerequest` и `test`) и хранит `ScriptVars` — то, что скрипты задали или
удалили в каждой области видимости. `ScriptVars::apply` накладывает их поверх
`Variables` запроса, поэтому разрешение работает как раньше. Ничего из того, что
задают скрипты, не пишется на диск.

`apix-script` выполняет скрипты одного события в новой среде QuickJS
(`rquickjs`; ограничения 10 s и 256 MB). Объект `pm` написан на JavaScript
(`prelude.js`): Rust передаёт контекст в виде JSON (неразрешённый запрос, ответ
для тестов, значения областей видимости из `project::scope_values`, предыдущие
`ScriptVars`, `pm.info`), скрипты выполняются один за другим, каждый обёрнутый
в функцию, а `__apix_output()` возвращает изменённый запрос и переменные,
результаты тестов, строки консоли, `setNextRequest` и `skipRequest` в виде JSON.
Благодаря тому, что API написан на JavaScript, на стороне Rust остаётся всего
несколько вызовов, а поведение Postman легко повторить.

`pm.sendRequest` вызывает нативную `__apix_send` с запросом в виде JSON; тот,
кто вызывает `apix_script::run`, передаёт `Sender`, который отправляет запрос и
блокируется до получения ответа (CLI — в новой среде выполнения в потоке
скрипта, приложение — в своей сетевой среде выполнения). Скрипты обёрнуты в
асинхронные функции, поэтому работают и стиль с callback, и `await`, а время
ожидания не учитывается в ограничении. `require` берётся из `libs.js`:
подмножества crypto-js (хеши и HMAC вычисляются в Rust через `__apix_hash` /
`__apix_hmac`), uuid, lodash, moment, ajv, tv4 и chai, написанные для Apix, а
не скачанные.

Отправка со скриптами: скрипты перед запросом, затем `ScriptVars::apply` и
разрешение переменных, HTTP-запрос, затем тестовые скрипты с `ResponseView`.
`apix_runner::exchange` делает это для `apix send`, `apix run` и Runner;
одиночная отправка в настольном приложении делает это в `script_run.rs`, со
скриптами в фоновом потоке и собственными скриптами запроса, взятыми из
редактора, сохранёнными или нет.

`apix_runner::run` принимает `Plan` (файлы запросов по порядку, переменные и
области видимости скриптов, строки данных, итерации, задержка, `bail`,
переопределения транспорта, начальное состояние скриптов) и проходит по нему:
на каждой итерации он накладывает строку данных (затем значения `--var`) поверх
переменных и `pm.iterationData`, следует `setNextRequest` по имени запроса,
ждёт между запросами и сообщает `Progress` (итерация, отправка, элемент готов)
в callback. `Control` приостанавливает или останавливает его из другого потока.
Он возвращает `RunReport` из `ItemResult`, который `report.rs` записывает в
виде JSON, JUnit XML (один набор на запрос и итерацию, один случай на тест,
случай статуса для запросов без тестов) и самодостаточной HTML-страницы.
`data.rs` читает CSV (RFC 4180, BOM, заголовки с `;`) и массивы JSON. CLI
печатает ход выполнения по мере поступления; Runner настольного приложения
(`workspace/runner_ui.rs`) выполняет запуск в сетевой среде выполнения и
несколько раз в секунду копирует ход выполнения из общей структуры `Live`;
представление остаётся в рабочей области, поэтому запуск переживает свой
диалог.

## Потоки и WebSocket (M6)

`HttpClient::send_with` сообщает `Progress::Head` (статус и заголовки), как
только они получены, а затем каждый `Progress::Chunk` тела; `send` — это
`send_with`, которого никто не слушает, и ответ всё равно содержит всё тело.
`apix_http::sse` читает тела `text/event-stream` по кускам (`SseParser`: любое
окончание строки, кусок может разрываться где угодно, `id` переносится,
незавершённое последнее событие отбрасывается). Парсер также хранит последний
id и последний `retry:` для повторного подключения: `reconnected()` запускает
парсер для следующего соединения с обоими значениями, а `reconnect_request`
добавляет `Last-Event-ID`. Приложение и CLI сами выполняют ожидание и
повторную отправку, поэтому Esc или Ctrl+C всегда это останавливают.

`apix_http::ws::connect` строит рукопожатие из запроса так, как его отправила
бы сторона HTTP (`prepare`: параметры, заголовки, авторизация; OAuth 2.0
сначала превращается в bearer-токен), добавляет `Sec-WebSocket-Protocol` из
`[websocket] subprotocols` и подключается через tokio-tungstenite. `wss://`
получает конфигурацию rustls из `apix_http::tls::client_config` (обычные
корневые сертификаты плюс доверенный CA, клиентский сертификат или
проверяющий, который принимает любой сертификат) — тот же модуль, который gRPC
использует без проверки. `WsConnection::run` отправляет то, что просит канал
`WsCommand`, и сообщает `WsEvent` (отправлено, получено, закрыто с кодом и
причиной, ошибка), пока одна из сторон не закроет соединение; на ping сервера
отвечает tungstenite. С `[websocket] ping_interval` он тоже отправляет ping со
счётчиком в качестве полезной нагрузки, сообщает время кругового обхода
соответствующего pong (`WsEvent::Pong`) и завершается с ошибкой, если ping всё
ещё без ответа, когда наступает время следующего. `MessageFormat` сообщения
(text, base64, hex) превращает его текст в `WsData` после подстановки
переменных.

В настольном приложении сетевая среда выполнения заполняет общие структуры
(`net::Incoming` для отправки, `net::SocketIncoming` для сокета), а задача
интерфейса читает их каждые 60–80 ms. Ответ-поток событий становится
`ResponseState::Streaming` (`workspace/stream_ui.rs`) с живым списком событий,
который следует за новыми событиями, если его не прокрутили вверх; Esc
превращает полученное в завершённый ответ. URL `ws://` переключает панель
запроса на вкладку «Сообщения» (`workspace/ws_editor.rs`), а панель ответа — на
`ResponseState::Socket` (`workspace/socket_ui.rs`). Оба состояния
направляются в свою вкладку, как завершённый ответ, поэтому поток или сокет
продолжает работать во вкладке на заднем плане. CLI печатает события и
сообщения из тех же callback.

## Socket.IO (M6)

`apix_http::socketio` говорит на Socket.IO 3/4 (протокол Engine.IO 4) поверх
описанного выше соединения WebSocket, поэтому рукопожатие, заголовки,
авторизация и настройки TLS те же. Запрос является запросом Socket.IO, если у
него есть таблица `[socketio]` (`SocketIoOptions`: пространство имён, путь,
авторизация); `handshake_request` превращает `http(s)://` в `ws(s)://`, берёт
пространство имён из параметров или пути URL, ставит на его место путь сервера
(`/socket.io/`) и добавляет `EIO=4&transport=websocket`. `connect` ждёт
пакет open от Engine.IO, отправляет CONNECT пространства имён с JSON
авторизации и ждёт ответа (`40…` с id сокета или `44…` с отказом), прежде чем
вернуть управление, поэтому неверный сервер, пространство имён или токен
приводят к ошибке так же, как неудачное рукопожатие.

`SioConnection::run` выполняет `WsConnection::run` рядом с переводчиком между
двумя каналами: `SioCommand::Emit` становится пакетом `EVENT` (`42…`, с id
подтверждения, если его просят; id считаются от 0) или `BINARY_EVENT`
(`45n-…`), у которого значения `{"$binary": "<base64>"}` заменяются
заполнителями и отправляются после него бинарными кадрами; полученные пакеты
становятся `SioEvent` (полученные события с id подтверждения, которого ждёт
сервер, наши подтверждения, сервер, заставляющий нас выйти, нечитаемые кадры),
а бинарные вложения собираются и возвращаются туда, где были их заполнители.
На ping Engine.IO (`2`) отправляется pong (`3`).

Настольное приложение держит одну вкладку «Сообщения» для обоих: у `WsEditor`
есть переключатель WebSocket/Socket.IO и поля Socket.IO, а `WsMessage` несёт
`event` и `ack`. `net::SocketIncoming` обобщён по типу события, и
`socket_ui.rs` следит за обоими видами соединений одним циклом, превращая
`SioEvent` в записи журнала с именем события и метками подтверждений. Тестовый
сервер в `apix-http/tests/common/socketio_server.rs` — это также пример
`socketio_server` (:8771).

## MQTT (M6)

`apix_proto::mqtt` оборачивает цикл событий rumqttc (MQTT 3.1.1; его TLS —
только через конфигурацию из `apix_http::tls::client_config`, поэтому он не
приносит собственного криптопровайдера). URL `mqtt://` или `mqtts://` делает
запрос запросом MQTT, как `grpc://` делает для gRPC; `[mqtt]` содержит client
id, сеанс, keep alive и подписки. `connect` опрашивает цикл событий до
получения CONNACK от брокера, поэтому отклонённый вход приводит к ошибке так
же, как неудачное рукопожатие.

`MqttConnection::run` выполняет два future рядом, никогда не отменяя опрос
цикла событий: один передаёт `MqttCommand` клиенту (который может ждать, когда
его очередь заполнена, а эту очередь опустошает опрос), другой следит за
соединением и сообщает `MqttEvent`. rumqttc сообщает id пакета каждого
исходящего пакета в том порядке, в каком они были переданы, поэтому очередь
сопоставляет публикации и подписки с их id, а PUBACK, PUBCOMP, SUBACK и
UNSUBACK брокера — с тем, что они подтверждают. Сообщение считается
отправленным, когда его пакет ушёл. Неверный топик или отклонённая подписка —
это событие, и соединение продолжается; закрытие и разрыв со стороны брокера
завершают его.

В настольном приложении `WsEditor` также содержит поля MQTT (решает URL, а
`Workspace` сообщает ему об этом), и `socket_ui.rs` следит за соединением тем же
циклом, что и для WebSocket и Socket.IO, превращая `MqttEvent` в строки журнала
по топикам. Тестовый брокер в `apix-proto/tests/common/broker.rs`
(подстановочные знаки, QoS 0–2, сохраняемые сообщения, отказы, TLS через любой
поток) — это также пример `mqtt_broker` (:8772).

## SOAP (M6)

SOAP не добавляет нового вида запросов: `apix_import::wsdl` превращает WSDL 1.1 в
обычные POST-запросы с XML-телами, поэтому всё, что работает с запросом,
работает и с ними. `apix_core::soap` содержит то, чем различаются версии
(заголовки, конверт), и читает ошибки (faults); `Response::soap_fault`
применяет это к XML-ответам, и runner считает запрос без тестов непрошедшим,
если в ответе есть fault, каким бы ни был статус.

Импортёр ничего не загружает сам. `Loader` проходит по `wsdl:import`,
`xsd:import` и `xsd:include`: он говорит, какое расположение читать следующим,
и получает текст обратно, поэтому CLI и настольное приложение читают файлы и
сеть каждый по-своему. Расположения разрешаются относительно своего документа,
документ из сети не может указывать на локальные файлы, а чтение
останавливается на 64 документах. Затем `Model` собирает сообщения, типы
портов, привязки, порты и глобальные элементы схем из всех документов с
ключами по пространству имён и имени. `Writer` строит примеры из узлов XSD
(roxmltree хранит их и разрешает `prefix:name` по собственным объявлениям
узла) и для каждого элемента решает, квалифицирован ли он, исходя из `form`,
`elementFormDefault` и того, глобальный ли он. Используемые пространства имён
попадают в конверт. Стек именованных типов, которые сейчас пишутся,
останавливает рекурсию.

Импорт по URL в приложении и CLI читает текст, а затем идёт тем же путём, что
и файл, поэтому подходит для любого формата. Тестовые WSDL в
`apix-import/tests/fixtures/` также питают пример `soap_server` (:8773).

## Схемы GraphQL (M6)

`apix_core::graphql` содержит стандартный `INTROSPECTION_QUERY`, `Schema`,
прочитанную из ответа на него (типы с полями, аргументами, входными полями,
значениями enum, интерфейсами и возможными типами; `TypeRef` сохраняет списки
и `!`), и `to_sdl`, который пишет сначала корневые типы и опускает встроенные
скаляры и типы `__`. Для редактора он читает запрос только до курсора:
`spot_at` разбивает текст на токены (комментарии, строки и `$variables`
отбрасываются) и проходит по стеку выборок, списков аргументов, входных
объектов и списков, следуя за псевдонимами, `... on Type`, фрагментами и
определениями переменных, чтобы сказать, что подходит в этом месте (`Spot`).
`suggestions` превращает это в метки с их типами и описаниями, упорядоченные
сначала по префиксу, затем по подстроке, устаревшие — в конце; `describe_at`
даёт Markdown для подсказки при наведении. Ничего не проверяется на
корректность: сломанный запрос всё равно дополняется настолько, насколько
возможно. Редактор переменных тоже дополняет: `variable_types` читает
объявления `$name: Type`, небольшой сканер JSON находит путь из ключей и
элементов списков до курсора и то, ключ или значение должно стоять там, а
`variable_suggestions` проходит по этому пути через входные поля и элементы
списков, чтобы предложить ещё не заданные переменные, входные поля, значения
enum (в виде строк JSON) и `true`/`false`; набираемая строка заменяется вместе
с кавычками, включая ту, которую закрыл редактор.

`apix_http::graphql::fetch_schema` отправляет запрос интроспекции как POST с
URL, заголовками, авторизацией и настройками запроса (запрос сначала
разрешается) и читает схему или говорит, почему её нет (статус не 2xx с
началом тела или `errors[0].message` сервера).

В приложении `workspace/graphql_ui.rs` реализует `CompletionProvider` и
`HoverProvider` из gpui-kit поверх общего `Rc<RefCell<Option<Rc<Schema>>>>`,
которым владеет редактор запроса; дополнения заменяют набираемое слово через
текстовую правку LSP. **Получить схему** в редакторе тела выпускает
`FetchSchema`; рабочая область строит запрос так же, как для отправки
(унаследованные авторизация и настройки, переменные), и загружает схему в
сетевой среде выполнения. Ответ каждого адреса хранится в
`<config>/Apix/graphql/<FNV-1a of the URL>.json` и загружается при открытии
запроса GraphQL. Представление SDL — это редактор только для чтения, который
заполняется при отрисовке, и только когда он показан.

## gRPC (M6)

`apix-grpc` выполняет вызовы без сгенерированного кода. Описание службы — это
`prost_reflect::DescriptorPool`: из файлов `.proto` запроса через protox (Rust,
без `protoc`; импорты ищутся в `import_paths` и рядом с каждым файлом,
общеизвестные типы Google встроены) или с сервера через рефлексию gRPC (v1,
затем v1alpha; файлы, которые сервер не отдал, запрашиваются по имени и затем
добавляются в порядке зависимостей). Сообщения — это `DynamicMessage`: JSON на
входе через поддержку serde в prost-reflect, JSON на выходе с именами полей из
`.proto` и показанными значениями по умолчанию. `DynamicCodec` подключает их к
tonic, поэтому `tonic::client::Grpc` выполняет все четыре вида методов
(унарный, серверный поток, клиентский поток, двунаправленный) через один
`Channel` (HTTP/2 на тех же hyper и rustls, которые уже использует HTTP-движок).

`apix_grpc::convert` строит описание из того, что есть, пробуя по очереди:
набор дескрипторов в JSON; текст `.proto`; `FileDescriptorProto`, который
встраивает сгенерированный код (`embedded.rs` знает, как каждый генератор
пишет эти байты, и у PHP это может быть даже не корректный текст); затем
объявления на языке программирования (`source.rs`: комментарии убираются,
блоки находятся, члены читаются по семейству языков, типы нормализуются, номера
берутся из аннотаций и кодировщиков ts-proto) или пример JSON (`json.rs`,
сохраняя порядок ключей, который `serde_json::Value` потерял бы). Последние два
проходят через небольшую `Schema`, которая выводится в `.proto`. `printer.rs`
записывает точное описание обратно как текст `.proto`, и ему верят, только если
этот текст компилируется в то же описание; иначе, или для нескольких файлов,
описание остаётся набором дескрипторов в JSON. `compare` сверяет описание с
описанием сервера, сопоставляя поля по имени, так как имена сообщений никогда
не передаются по сети. `described` хранит порядок: описание в запросе, его
файлы, рефлексия; догадка сначала пробует рефлексию и уступает ей. `call`
сообщает о полях, которые `DynamicMessage` не смог разместить
(`CallEvent::Note`), потому что больше никто этого не сделает.

Заголовки и авторизация запроса становятся метаданными (Bearer, Basic,
заголовок API-ключа, OAuth 2.0 через `apix_http::oauth2`; ключи `-bin` в
base64); типы авторизации, которые подписывают HTTP-запросы, отклоняются с
указанием причины. Тайм-аут, клиентский сертификат и доверенный CA берутся из
настроек запроса. При выключенной проверке TLS tonic (у которого такого
переключателя нет) получает обычный адрес `http://` и настоящий источник
`https`, а TLS выполняет собственный коннектор (`insecure.rs`): rustls с ALPN h2
и проверяющим, который принимает любой сертификат, но всё же проверяет подписи
рукопожатия. `call` сообщает события `Sent`, `Headers` и `Received` по мере их
возникновения и завершается `CallOutcome`: код состояния и сообщение,
метаданные ответа, трейлеры и все сообщения. Статус, отличный от OK, — это
результат, а не ошибка; ошибки — это то, что не даёт вызову состояться (нет
соединения, нет описания, сообщение не подходит к своему типу).

В приложении URL `grpc://` превращает вкладку «Тело» во вкладку «Сообщение»
(`workspace/grpc_editor.rs`): выбор метода с поиском, который заполняется
кнопкой **Загрузить методы**, файлы `.proto` и сообщение с примером,
построенным из входного типа. Вызов выполняется в сетевой среде выполнения и
заполняет общую структуру, которую интерфейс читает каждые 60 ms; панель ответа
— это журнал (`ResponseState::Grpc`, `workspace/grpc_ui.rs`), как у WebSocket,
а Esc прерывает вызов. CLI печатает унарный ответ целиком, а потоки — построчно,
и `apix schema` записывает службу текстом, похожим на `.proto`.

Запуски вызывают запросы gRPC через `apix_grpc::send_for_tests`, который
превращает `CallOutcome` в `apix_http::Response` (`CallOutcome::to_response`):
HTTP-статус, которому соответствует код (сопоставление Google), с именем кода
в качестве причины, метаданные и трейлеры плюс `grpc-status` и `grpc-message`
как заголовки, а сообщение (список JSON для серверного потока) как тело.
Тестовым скриптам, проверкам и отчётам тогда не нужно ничего специфичного для
gRPC. История хранит вызов с заданным `Summary::grpc`: статус — это код gRPC,
у трейлеров и сообщения статуса свои поля, а тело — это журнал
(`[{"at_ms", "sent", "message"}]`), который `grpc_ui::restored` превращает
обратно в представление журнала.

## Параллельные запуски и мониторы (M7)

`Plan::parallel` больше единицы выполняет столько итераций одновременно
(`buffer_unordered` из `futures_util` в собственной задаче запуска, без
потоков): каждая итерация отправляет свои запросы по порядку со своей копией
состояния скриптов, сбой при `bail` останавливает остальные, а отчёт
сортируется по итерациям после завершения. Ход выполнения проходит через
мьютекс вокруг callback вызывающего.

`apix_core::monitor` описывает `[[monitor]]` в `apix.toml` (имя, `every`,
`run`, окружение, webhook, включён ли) и читает интервалы; `apix_runner::monitor`
выполняет один монитор (`plan` разрешает переменные как `apix run`: окружение
монитора, `APIX_VAR_*`, затем закреплённые значения), подводит итог
(`Outcome`), ведёт `Log` в формате JSON lines для каждого монитора
(`<config>/Apix/monitors/<hash of the collection>-<name>.jsonl`, последние 500),
решает, когда каждому пора запускаться (`Scheduler`: монитору, увиденному
впервые, пора, когда с его последнего записанного запуска прошёл его интервал),
и сообщает webhook, когда меняется состояние (`change`, `notify`).
`apix monitor` и настольное приложение (`workspace/monitors_ui.rs`: тикер раз в
секунду, пока включена настройка, по одному запуску за раз в сетевой среде
выполнения) оба используют его, поэтому у них общий журнал.

## Git (M7)

`apix_core::git` запускает уже установленную программу `git` (без библиотеки
git, поэтому к бинарнику ничего не добавляется, а собственные настройки, хуки и
учётные данные пользователя действуют). `Repo` открывается в папке коллекции
или проекта, и каждая команда выполняется там с `--relative`, поэтому пути
указываются относительно этой папки, а коллекция внутри большего репозитория
видит только свои файлы. `changes_since(rev)` — это
`git diff --merge-base rev` (с того места, где ветка отошла от `rev`, как в
pull request) плюс неотслеживаемые файлы; без истории (поверхностный клон) он
сравнивает с самим `rev` и сообщает об этом. `show(rev, path)` читает файл в
коммите.

`git::affected` сопоставляет изменённые файлы с запросами по их роли
(`git::role_of`): файл запроса или его скрипты `<stem>.*.js` → этот запрос;
`folder.toml` или `_folder.*.js` → запросы в этой папке; `apix.toml`,
`_collection.*.js`, `environments/*.toml`, файл проекта или окружения проекта
→ все; любой другой файл → запросы, файл которых на него ссылается.
`apix run --changed` оставляет эти запросы, а отчёт записывает выбор
(`RunReport::selection`).

`apix_core::diff` сравнивает две версии файла по смыслу: запросы разбираются в
`Request` и сериализуются в JSON (поэтому значения по умолчанию и
форматирование не важны), остальной TOML — в значения, скрипты и другой текст —
построчно (наибольшая общая подпоследовательность с обрезанными общими началом
и концом). Списки строк с уникальным `key` или `name` (заголовки, query,
`[[example]]`) становятся таблицами с ключом по нему, поэтому строки
сопоставляются по имени; поля называются по своему пути (`headers.Accept`,
`body.json`). Удалённый и добавленный запрос с одинаковым содержимым становятся
одним перемещением. `apix diff` печатает результат как текст, Markdown или
JSON.

`RunReport::to_markdown` записывает запуск для GitHub (по строке таблицы на
запрос, сбои в открытом `<details>`), начиная со скрытого маркера
`<!-- apix-run: <name> -->`, который ищет шаг комментария в action, чтобы
отредактировать свой прежний комментарий. Он укладывается в ограничение GitHub
в 65 536 символов.

Настольное приложение (`workspace/git_ui.rs`) в фоне читает ветку и
`git status` для открытой папки после каждой перезагрузки и при активации окна
и хранит карту изменённых путей для отметок в боковой панели; запрос, у
которого изменились собственные скрипты, считается изменённым.

Окно Git (`workspace/git_panel.rs`) использует тот же `Repo`: `working_changes`
для списка, `show("HEAD", path)` против файла на диске через `diff::file` для
выбранного файла, а также `commit_folder` (`git add -A -- .`, затем
`git commit -- .`, то есть только открытая папка), `branches`, `switch`,
`create_branch` (`switch -c`), `pull` (`--ff-only`), `push` (`-u origin
<branch>`, когда нет upstream) и `log` (хеш, время, тема). Git запускается с
`GIT_TERMINAL_PROMPT=0`, поэтому удалённый репозиторий, которому нужен пароль,
завершается сообщением git, а не ждёт ввода; помощники учётных данных
по-прежнему работают. Каждая операция выполняется в фоне и обновляет строку
состояния.

## ИИ-помощник

`apix_core::ai` вручную строит запрос к одному из трёх провайдеров (у Rust нет
для них официального SDK) и читает ответ. `Provider` (`anthropic`, `openai`,
`google`) даёт модель по умолчанию, учётную запись ключа в связке ключей
(`ai:<provider>-api-key`, через `apix_vault::keychain::save_text`), его
переменную окружения и URL. Anthropic: `POST /v1/messages` с `x-api-key`,
`anthropic-version: 2026-10-21`, `claude-opus-5-5` и, для модели по
умолчанию, запасными вариантами на стороне сервера (`fallbacks: "default"`,
beta `server-side-fallback-2026-07-01`); причина остановки `refusal`
становится сообщением. OpenAI: `POST /v1/chat/completions` с bearer-ключом,
системным и пользовательским сообщением; поле `refusal` считается отказом.
Google: `POST /v1beta/models/{model}:generateContent` с `x-goog-api-key`,
`systemInstruction` и `contents`; завершения `SAFETY` и заблокированные
запросы считаются отказом, части с размышлениями пропускаются. Каждый запрос к
модели несёт обмен (`Context::describe`: заголовки с учётными данными скрыты,
тела обрезаны до 12 KB), задачу и код языка приложения. `models_request` /
`models` перечисляют, что может использовать ключ (у OpenAI только модели чата,
у Google — модели, поддерживающие `generateContent`). `APIX_AI_URL` заменяет
базовый URL для тестов. Приложение (`workspace/ai_ui.rs`) отправляет через
`net::send`, добавляет тесты через `ScriptEditor::append_test` и показывает
объяснения в диалоге; настройки хранят `ai_provider` и `ai_model`.

## Сервер MCP

`apix mcp` (`apix-cli/src/mcp.rs`) читает по одному сообщению JSON-RPC 2.0 на
строку из стандартного ввода и пишет по одному ответу на строку в стандартный
вывод (транспорт stdio в MCP; метка порядка байтов перед первой строкой
пропускается). `initialize` отвечает запрошенной версией протокола, если знает
её (2025-06-18, 2025-03-26, 2024-11-05), и самой новой в противном случае, и
предлагает только инструменты; на уведомления ответа нет, неизвестные методы
дают ошибку -32601. Результаты `tools/call` несут JSON и как текст, и как
`structuredContent`, а неуспешный инструмент — это результат с `isError`, а не
ошибка протокола, чтобы агент мог прочитать причину. Пути от агента
присоединяются к корню коллекции, `..` разрешается, а пути за её пределами
отклоняются. `send_request` идёт через `apix_runner::exchange` (скрипты,
переменные, тесты), `run_requests` — через `apix_runner::run`; переменные
берутся из того же `VarArgs::resolve`, что и в других командах, а `variables`
агента выступают как `--var`. CLI работает в потоке размером 16 MB, так как
общий future команд перерос стек главного потока в Windows.

## Сценарии

`apix_core::flow` — это файл: у `Flow` есть узлы (`NodeKind::Request`,
`Check`, `Set`, `Delay`, развёрнутые в каждую таблицу `[[node]]` вместе с её
id и положением) и связи от исхода узла (`ok`/`fail`, `yes`/`no`, `next`) к
другому узлу. `problems()` перечисляет то, что мешает сценарию запуститься;
`Seen` — последний ответ, а `Seen::subject` читает `status`, `time`, `body`,
`header:Name` или фильтр JSONPath либо jq через `apix_core::filter`. Файлы
`.flow` могут лежать где угодно в коллекции; боковая панель их игнорирует.

`apix_runner::flow::run` проходит по графу от начального узла. Узел запроса
идёт через `exchange`, как при запуске, поэтому скрипты, тесты и переменные
`pm.*` работают; то, что он сохраняет, задаётся в локальной области видимости
состояния скриптов, которая важнее окружения для следующих за ним узлов, как
это сделал бы `pm.variables.set`. Проверка, предмет которой — текст, разрешает
`{{variables}}` и не имеет значения, если какая-то переменная не определена.
Запуск сообщает о каждом шаге (`FlowProgress`) и останавливается после 1000
шагов или через `Control`. `FlowReport::to_run_report` повторно использует
отчёты запусков (JUnit, HTML, Markdown). Настольный редактор
(`workspace/flows_ui.rs`) рисует узлы как позиционированные элементы, а связи —
на холсте: связи вперёд — кривыми, связи назад — линиями в обход узлов; он
выполняет сценарий в сетевой среде выполнения и читает ход выполнения по
таймеру, как Runner.

## Плагины

`apix-plugins` выполняет плагины WebAssembly с помощью `wasmi` 2 —
интерпретатора: без JIT, поэтому из плагина не создаётся нативный код, и он
собирается везде, где собирается Rust. Модуль не может ничего импортировать,
поэтому у плагина вообще нет функций хоста (ни сети, ни файлов, ни часов, ни
случайности); он экспортирует `memory`, `apix_alloc`, `apix_manifest` и
`apix_call`, а ответы — это JSON, передаваемый как `ptr << 32 | len`. Каждый
вызов заново создаёт экземпляр модуля (без состояния между вызовами) с 2·10⁹
единицами топлива и ограничением памяти 256 MB, в потоке со стеком 64 MB;
исчерпание топлива сообщается как «выполнялся слишком долго». Манифест
читается один раз при загрузке плагина; его `name` должно соответствовать
`[a-z0-9-]`. `installed()` кэширует папку плагинов (`<config>/Apix/plugins` или
`APIX_PLUGINS_DIR`) до вызова `reload()`.

Хуки встречаются с остальным Apix в трёх местах: `Auth::Plugin { plugin,
config }` в модели, который разрешается как другая авторизация (переменные в
конфигурации) и применяется `apix_http::prepare` к окончательному запросу;
`apix_import::plugin::plan`, который превращает ответ импортёра в файлы
запросов; и визуализатор ответа (`VisualMode::Plugin`), который выполняет плагин
вне потока интерфейса и рисует таблицу или текст. wasmi собирается с
`opt-level = 3` и без отладочных проверок даже в debug-сборках, так как его
диспетчеризация опирается на хвостовые вызовы, которые иначе исчерпывают стек.

## Сравнение ответов

`apix_core::compare` принимает два `Snapshot` (метка, статус, заголовки, тело,
время). Заголовки сравниваются по имени в нижнем регистре, несколько заголовков
с одним именем объединяются; те, что входят в `VOLATILE` (даты, кэширование,
id запросов и трассировки, ограничения частоты, способ передачи тела),
только учитываются как опущенные. Два тела JSON проходят через `by_id`,
который превращает списки записей с уникальными значениями `id` / `_id` /
`uuid` / `key` в таблицы с ключами `[id=…]`, а затем через
`diff::fields_as_they_are` (обход из сравнения запросов без сопоставления по
key/name, которое подходит для файлов запросов, но не для данных); другой
текст сравнивается построчно, всё остальное — только по размеру. Окно
приложения «Сравнить ответы» (`workspace/compare_ui.rs`) берёт более раннюю
сторону из истории (записи с тем же файлом запроса или с тем же методом и URL)
или отправляет запрос, разрешённый с переменными другого окружения;
`apix compare` отправляет его в двух окружениях.

## Нагрузочное тестирование

`apix_http::load::Load` строит один клиент reqwest для разрешённого запроса
(настройки TLS запроса через `tls::client_config`, его прокси, тайм-аут и
политика перенаправлений, неограниченный пул простаивающих соединений), а
`hit()` отправляет его, считая байты тела без распаковки; OAuth 2.0 один раз
превращается в bearer-токен, Digest отклоняется.
`apix_runner::bench::Bench::run` запускает `concurrency` исполнителей в одном
`FuturesUnordered`; каждый берёт следующий номер запроса из атомарного
счётчика, пока количество, крайний срок или `stop()` не скажут «нет», а при
заданной частоте ждёт до `start + n / rate`. Каждое обращение записывается под
мьютексом: его задержка в микросекундах (`u32` на запрос, так что миллион
запросов — это 4 MB), статус, ошибка по виду («не удалось подключиться»,
«истекло время ожидания», …), байты и корзина на каждую секунду. `summary()`
можно вызывать во время работы: он сортирует копию задержек для перцентилей по
ближайшему рангу. CLI выполняет тест в собственной среде выполнения с потоком
на ядро и печатает по строке в секунду; приложение выполняет его в своей
сетевой среде выполнения и перерисовывается четыре раза в секунду.

## Маршрут и карта

`apix-route` запускает системный инструмент, как `apix_core::git` запускает
git: `tracert -d -h N -w 1000` в Windows, `traceroute -n -q 1 -w 1 -m N` в
macOS и Linux, `tracepath -n -m N`, если traceroute нет. Ни одному из них не
нужны права администратора, которые в Windows понадобились бы для
самостоятельной отправки ICMP. `parse_line` читает строку любого из них только
по числам и адресам (сначала номер узла, каждое `N ms`, первое слово, которое
разбирается как адрес), поэтому переведённая Windows в своей кодовой странице
читается так же; время узла — лучшая из его попыток, `<1 ms` считается за
половину миллисекунды. `Trace` перебирает узлы по мере того, как инструмент
их печатает, и завершает его при удалении или остановке.

`Geo` открывает файл MaxMind DB (`maxminddb`) и даёт `Place` (широта, долгота,
название города на английском, страна ISO) для публичных адресов; частные,
loopback, link-local, CGNAT и multicast-адреса никогда не ищутся. База — это
первый найденный `.mmdb` в `<config>/Apix/geo`; `install` распаковывает
скачанное (gzip), проверяет, что оно открывается, и только после этого
заменяет старую. `dbip_urls` даёт адрес DB-IP Lite за этот и за прошлый месяц
(`APIX_GEO_URL` их заменяет). Карта — это равнопромежуточная проекция
`land::LAND`: континенты и крупные острова, нарисованные вручную с точностью
около двух градусов (с Чёрным и Каспийским морями в `land::WATER`), поэтому
никакие картографические данные не скачиваются и не лицензируются. Окно
настольного приложения (`workspace/route_ui.rs`) выполняет трассировку в
потоке, размещает узлы по мере поступления, читает базу один раз за запуск
приложения и рисует карту путями GPUI. `apix trace` печатает узлы с их
местами и расстоянием каждого перехода больше 100 km.

## Проверка обновлений

`apix_core::update` строит запрос (`releases/latest` на GitHub для 11R5/Apix,
`User-Agent: Apix/<version>`, тайм-аут 10 s; `APIX_UPDATE_URL` направляет его
в другое место) и читает ответ: `Version` разбирает `v1.2.3`, `1.2` и
предварительные выпуски (`1.0.0-rc.1` идёт раньше `1.0.0`, числовые части
сравниваются по значению), 404 означает, что ещё ничего не опубликовано,
другие ошибки несут сообщение GitHub. CLI (`apix update`) отправляет его своим
клиентом; приложение (`workspace/update_ui.rs`) — через `net::send` при
запуске, когда включена `settings.check_updates` (показывается только более
новый выпуск), и из **Справка › Проверить обновления…** (показывается любой
ответ). Ничего не скачивается и не устанавливается.

## Темы

`theme.rs` хранит цвета. `ThemeDef` — это тема (встроенная или прочитанная из
`<config>/Apix/themes/*.toml`; цвета, которые файл не задаёт, берутся из
Obsidian или Daylight) с `Colors` и признаком тёмной/светлой темы.
`Palette::build` превращает её в то, чем рисуют представления: настройку
акцентного цвета (именованный цвет с тёмным и более глубоким светлым оттенком
или `#RRGGBB`), текст на акцентном цвете, выбранный по относительной яркости,
оттенки наведения и полей ввода для тёмной или светлой темы и настройку
прозрачности: альфа фона окна равна `1 - t`, панели становятся прозрачными со
скоростью 60% от этой, границы светлеют к белому по мере роста `t`, а светлые
темы используют 70% от `t`. `from_settings` выбирает тёмную или светлую тему
по настройке внешнего вида, а для «как в системе» — по
`App::window_appearance`.

Корневое представление gpui-kit рисует `Theme::background` под всем окном, что
скрыло бы размытие ОС, поэтому при любой прозрачности он делается прозрачным,
а диалоги получают собственный фон через `bidi::DialogBidi`, который
используют все диалоги. Размытие делает ОС: `WindowBackgroundAppearance::Blurred`
— это acrylic в Windows (`SetWindowCompositionAttribute`) и vibrancy в macOS.

Представления никогда не хранят копию палитры: они вызывают `theme::current()`
при отрисовке. `theme::set` сохраняет новую палитру, направляет на неё тему
компонентов gpui-kit (переключая её режим, чтобы цвета редактора кода
следовали за ней), делает фон каждого окна размытым или непрозрачным и
обновляет окна, поэтому изменение видно сразу. Рабочая область следит за
внешним видом окна и вызывает её снова, когда система переключается между
светлым и тёмным режимом.

## Языки (M4)

Каждый текст в интерфейсе настольного приложения проходит через ключ:
`tr!("menu.file")` (тонкая обёртка над `rust_i18n::t!`, которая возвращает
`SharedString` для показа; `tr_plain!` даёт тот же текст для того, что
сохраняется, например для имени нового запроса по умолчанию).
rust-i18n — та же система, которую использует gpui-kit, поэтому оба следуют
одной локали на весь процесс; для китайского используется `zh-CN` — код,
который используют собственные тексты gpui-kit. Каждый язык — это один плоский
файл, `crates/apix-desktop/locales/<code>.yml` (по одной паре `key: value` на
строку, отсортировано, заполнители `%{name}`), встроенный в бинарник;
`build.rs` пересобирает при изменении файла. Отсутствующий текст заменяется
английским, а модульный тест падает, если в языке нет ключа, есть неизвестный
ключ или используются другие заполнители, чем в английском. Предложения — это
целые ключи с заполнителями, а не склейки из кусков, потому что порядок слов в
языках разный.

Язык выбирается в настройках (или при первом запуске следует языку системы) и
переключается сразу: тексты читаются при каждой отрисовке, а немногие тексты,
хранящиеся внутри виджетов (заполнители полей ввода, пункты списков выбора),
задаются заново через `Workspace::retranslate`. Глифы для японского,
китайского и арабского берутся из резервных шрифтов платформы (DirectWrite,
Core Text, fontconfig) рядом со встроенным Inter. Арабский текст формируется и
размещается справа налево; в Windows для этого нужен `vendor/gpui-pre-windows`
— бэкенд DirectWrite из gpui 0.3.9 с исправленным размещением
последовательностей глифов (подставляется через patch из `Cargo.toml` рабочего
пространства; уберите его, когда это исправят в исходном проекте). gpui не
умеет переносить текст справа налево: он формирует абзац как одну строку и
режет его по x-позициям глифов, которые, как он предполагает, растут слева
направо. Поэтому текст, который может переноситься (заметки, подсказки,
описания, сообщения), проходит через `bidi::para`, который в RTL разбивает
текст по пробелам в порядке чтения, измеряя каждую строку-кандидата, и рисует
каждую строку без переноса (`src/bidi/paragraph.rs`). В других языках это
обычный текст gpui. gpui также раскладывает каждую строку с базовым
направлением слева направо, поэтому в RTL-языке `tr!` оборачивает каждый текст
во встраивание справа налево (U+202B…U+202C; DirectWrite игнорирует более новые
изоляторы). Тогда предложение, которое начинается или заканчивается латинским
словом («URL», «OAuth 2.0», «Ctrl+S»), всё равно читается справа налево, а
`i18n::display` делает то же для составных текстов, таких как строка
состояния. Эти метки никогда не попадают в файлы: сохраняемые тексты используют
`tr_plain!`. Сообщения об ошибках из crates движка остаются на английском.

В языке с письмом справа налево (`Language::rtl`, арабский) окно отражается:
боковая панель переходит вправо, панель ответа — слева от панели запроса,
кнопки управления окном — влево, а меню, полосы вкладок, строки форм и строка
состояния идут справа, с текстом, выровненным по правому краю. В GPUI нет
направления раскладки, поэтому это делает `src/bidi.rs`: трейт `Bidi` для
каждого стилизуемого элемента (`dir_row` разворачивает строку, `text_start` /
`text_end`, отступы `ps` / `pe` и `border_e_1` выбирают сторону по
направлению, `ltr` прижимает текст влево), `tab_bar` / `fill_tabs` для `TabBar`
из gpui-kit (вкладки передаются в обратном порядке, индексы отображаются
обратно) и `bidi_title` для диалогов (в RTL кнопка закрытия переходит в строку
заголовка слева). Помощники читают язык во время отрисовки представления,
поэтому смена языка сразу отражает окно. Просмотрщики кода и ответа, строка
URL, таблицы ключ–значение (параметры, заголовки, поля форм, переменные) и
заголовки ответа остаются слева направо во всех языках. Всплывающие меню и
кнопки gpui-kit сохраняют свою внутреннюю раскладку слева направо (сочетание
клавиш справа, иконка перед подписью); меню открываются от своей кнопки влево.

Добавление языка: скопируйте `locales/en.yml` в `locales/<code>.yml`,
переведите значения и добавьте одну строку в `LANGUAGES` в `src/i18n.rs`.

Пользовательская документация хранится отдельно от плана, по одной папке на
язык (`Docs/<code>/`: руководство пользователя, архитектура, технические
заметки, рабочие процессы, изображения), и перечислена в `Docs/languages.toml`.
Источник — английский; каждый перевод записывает английскую версию, с которой
он сделан, поэтому устаревшие переводы видны.

## Модель потоков (настольное приложение)

- GPUI владеет главным потоком, который выполняет цикл событий и отрисовку.
- Одна многопоточная **среда выполнения tokio** запускается один раз в фоновом
  потоке. Она нужна reqwest, tonic и tungstenite.
- Интерфейс отправляет работу в tokio и получает результат в задаче GPUI
  (`cx.spawn_in`). Удаление этой задачи прерывает запрос, поэтому Esc и
  повторная отправка чисто отменяют его.
- После получения ответа тело форматируется и индексируется в фоновом
  исполнителе GPUI, прежде чем его увидит интерфейс. Форматирование использует
  `apix_core::text::pretty_json` — однопроходный переформатировщик отступов,
  который не строит дерево и сохраняет числа точно такими, как они были
  отправлены.

## Просмотр больших ответов

Тела от 512 KB используют `large_view.rs` вместо редактора кода:

- `apix_core::text::RowIndex` записывает, где начинается каждая отображаемая
  строка, по 8 байт на строку. Строки длиннее 2 KB (минифицированный JSON)
  разбиваются на несколько строк.
- Позиция прокрутки — это **номер строки**, а не смещение в пикселях. Десять
  миллионов строк по 20 px дали бы около 200 миллионов px — далеко за пределами
  диапазона, где пиксели `f32` точны. Просмотрщик раскладывает только ~120
  строк, которые помещаются на экране. Он обрабатывает колесо мыши, собственную
  полосу прокрутки и клавиатуру (↑ ↓ PgUp PgDn, Ctrl+Home/End).
- Вкладка «Исходный» большого тела JSON строится, только когда её открывают.
- Ctrl+F ищет по всему тексту в фоновом потоке (`regex` без учёта регистра по
  буквальному запросу) и хранит до 100,000 диапазонов байтов;
  `RowIndex::row_of` находит строку совпадения двоичным поиском, и только
  строки на экране ищут свои совпадения, чтобы их подсветить.

Меньшие тела показываются в редакторе кода, у которого включена собственная
панель поиска. Фильтр над вкладкой «Форматированный» (`workspace/filter_ui.rs`)
выполняет `apix_core::filter` вне потока интерфейса через 250 ms после
последнего нажатия клавиши: JSONPath через `serde_json_path` для выражения,
начинающегося с `$`, иначе jq через `jaq`, не больше 10,000 результатов jq. Его
результат — `Document`, как и любое тело, поэтому отфильтрованное большое тело
может попасть в редактор, и наоборот.

Измерено в Windows в release-сборке для 100 MB минифицированного JSON с
локального сервера (`cargo run -p apix-http --release --example big_json_server`):
ответ появляется на экране примерно через 0.33 s после Enter. Это включает
передачу, форматирование в 9.6 миллиона строк, индексацию и первый кадр. Память
— около 407 MB с загруженным телом против 69 MB в простое.
