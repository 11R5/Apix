## Отправка и сохранение первого запроса

1. **Файл › Новая коллекция…**, выберите пустую папку и дайте ей имя.
2. Ctrl+N открывает новый запрос GET. Введите `https://jsonplaceholder.typicode.com/users`.
3. Ctrl+Enter отправляет его; ответ появляется справа.
4. Ctrl+S сохраняет его как новый файл в папке коллекции. Щёлкните по нему
   правой кнопкой в боковой панели › **Переименовать**, чтобы дать ему имя,
   например «List users».

Файл — это обычный TOML, который можно читать и править:

```toml
name = "List users"
url = "https://jsonplaceholder.typicode.com/users"
```

## Коллекция в git

Коллекция — это папка:

```
my-api/
├── apix.toml                имя коллекции, переменные, общая авторизация
├── environments/
│   ├── staging.toml         общие значения
│   └── staging.local.toml   секретные значения (в gitignore)
├── users/
│   ├── folder.toml          необязательно: авторизация для запросов этой папки
│   ├── list-users.apix
│   └── create-user.apix
└── health.apix
```

Коммитьте всё, кроме `*.local.toml`; Apix сам добавляет этот шаблон в
`.gitignore`, когда впервые записывает секрет. Каждый запрос — отдельный
небольшой файл, поэтому ревью и слияния остаются читаемыми.

## Работа с dev, staging и production

1. Откройте **Окружение › Переменные и окружения…** (Ctrl+E).
2. Добавьте окружения с именами `dev`, `staging` и `prod`, у каждого свой `base_url`.
3. Используйте в запросах `{{base_url}}/users`.
4. Выберите окружение в боковой панели, под именем коллекции.

Значения, которые не должны попасть в коммит (токены, пароли), получают
отметку **Секрет**. Каждый участник команды хранит свой `*.local.toml`.
Переменная, заданная на уровне коллекции, — это значение по умолчанию, которое
окружения могут переопределить.

## Общий доступ к коллекции с секретами

Когда чувствительна вся коллекция (внутренние URL, примеры данных клиентов,
долгоживущие ключи), зашифруйте её:

1. **Файл › Зашифровать эту коллекцию…** и выберите пароль.
2. Сохраните показанный **ключ восстановления** в своём менеджере паролей.
3. Закоммитьте папку. На диске это набор зашифрованных объектов; скрыты даже
   имена файлов.

Участники команды открывают папку в Apix и вводят пароль. В терминале или CI:

```sh
APIX_PASSWORD='…' apix run my-api --env staging
```

`apix decrypt my-api --out my-api-plain` записывает незашифрованную копию;
с `--recovery` вместо пароля используется ключ восстановления.

## Переход с Postman

1. В Postman экспортируйте коллекцию (Collection v2.1) и каждое окружение.
2. В Apix выберите **Файл › Импорт…** или перетащите файлы в окно.
   Или в терминале:

   ```sh
   apix import "My API.postman_collection.json"            # создаёт ./my-api
   apix import "Staging.postman_environment.json" --into my-api
   ```

3. Прочитайте отчёт об импорте: всё, что не удалось перенести, перечислено
   там (например, авторизация NTLM или сохранённые примеры ответов).
4. Скрипты перед запросом и тестовые скрипты сохраняются как файлы `.js`
   рядом со своими запросами; Apix пока их не запускает.
5. Для OAuth 2.0 с authorization code grant зарегистрируйте у своего
   провайдера удостоверений loopback-адрес перенаправления, например
   `http://127.0.0.1:8765/callback`, и укажите его на вкладке «Авторизация».

Переносите всё рабочее пространство? Используйте в Postman **Settings › Data › Export data**,
затем откройте папку (или zip) в Apix или перетащите её в окно: каждая
коллекция, окружение и глобальные переменные переходят как один проект
(`apix import postman-export.zip` делает то же самое). Участники команды,
которые остаются на Postman, получают вашу коллекцию обратно через
**Экспорт в Postman…**.

## Запуск коллекции в CI

`apix run` отправляет все запросы коллекции в порядке боковой панели и
завершается с ненулевым кодом, если какой-то из них не прошёл, поэтому
подходит как шаг CI:

```sh
apix run my-api --env staging --var token="$API_TOKEN"
```

Запросы с тестами (скриптами или проверками) проходят или не проходят по своим
тестам; остальные — по коду состояния. Вывод перечисляет каждый тест под его
запросом:

```text
create.apix                              201 Created  466.7 ms · 42 B
  │ new id 101
  ✓ created
get.apix                                 200 OK  174.7 ms · 292 B
  ✓ status 200
  ✗ has the right id expected 1 to equal 2

1 passed, 1 failed (1 failed tests)
```

То, что задаёт скрипт (`pm.environment.set`, `pm.variables.set`), переходит в
следующие запросы запуска, а `pm.execution.setNextRequest("name")` переходит к
другому запросу (`null` завершает итерацию).

Параметры:

| Параметр | Что делает |
|---|---|
| `apix run my-api/users` | Только запросы из папки (или один файл запроса) |
| `-d, --data users.csv` | Запуск по данным: каждая строка CSV или JSON — одна итерация, её столбцы — переменные (`{{email}}`, `pm.iterationData.get("email")`) |
| `-n, --iterations 5` | Пройти по запросам 5 раз (по умолчанию: по разу на строку данных, иначе один раз) |
| `--delay 200` | Ждать 200 ms между запросами |
| `--bail` | Остановиться на первом непрошедшем запросе |
| `-p, --parallel 4` | Выполнять 4 итерации одновременно, как 4 пользователя; каждая отправляет свои запросы по порядку и держит то, что задали её скрипты, при себе |
| `--junit report.xml` | Отчёт JUnit XML, который сервисы CI показывают как список тестов |
| `--json report.json` / `--html report.html` | Всё в виде JSON или страница, которая открывается в любом браузере |
| `--markdown report.md` | Сводка для комментария к pull request или сводки задачи CI (см. ниже) |
| `--changed` / `--changed=origin/main` | Только запросы, которых касается изменение (см. ниже) |
| `--timeout 10`, `-k`, `--proxy URL` | Переопределить транспортные настройки запросов |
| `--env-file .env` | Переменные из файла dotenv (см. ниже) |

Файл данных выглядит так; значения извне коллекции (`--var` и описанные ниже)
важнее его столбцов:

```csv
id,name
1,Leanne Graham
2,Ervin Howell
```

### Секреты в CI

Секреты не попадают в git (файлы `.local.toml` игнорируются, связка ключей
находится на вашем компьютере), поэтому конвейер передаёт их одним из трёх
способов, и каждый следующий важнее предыдущего:

1. `--env-file .env`: файл dotenv со строками `NAME=value` (допускаются
   комментарии `#`, кавычки, `export`).
2. Переменные окружения `APIX_VAR_<NAME>`: `APIX_VAR_TOKEN` заполняет
   `{{token}}`. Секреты CI обычно пишут заглавными буквами, поэтому имя
   совпадает с переменной, которую задаёт коллекция или используют её
   запросы, независимо от регистра.
3. `--var name=value`.

Все три важнее значений окружения (и столбцов файла данных). `apix` выводит в
stderr, какие имена откуда взяты, но никогда не значения.

```sh
APIX_VAR_TOKEN="$API_TOKEN" apix run api --env staging
```

### GitHub Actions

Репозиторий также является GitHub Action. Он запускает коллекцию и пишет
отчёты JUnit и HTML. При использовании с тегом выпуска он скачивает `apix` этого
выпуска (секунды); с веткой или коммитом он собирает `apix` в первый раз и
кэширует его, а `apix-version: latest` (или `0.1.1`) вместо этого скачивает
выпуск:

```yaml
- uses: 11R5/Apix@v0.1.1        # выпуск: apix скачивается, а не собирается
  with:
    path: api
    environment: staging        # также: data, iterations, delay, bail, env-file, junit, html, json, markdown, changed, diff, comment, args, apix-version
  env:
    APIX_VAR_TOKEN: ${{ secrets.API_TOKEN }}
```

[examples/ci/github-actions.yml](../../examples/ci/github-actions.yml) — это
полный workflow: он запускает коллекцию по разу для каждого окружения (матрица
из `test` и `staging`), показывает результаты JUnit на странице запуска и
сохраняет отчёты HTML. Action также добавляет свою сводку Markdown на страницу
задачи.

## Только изменённое: запуски с учётом git

Коллекция — это папка в git, поэтому `apix` может спросить у git, чего
коснулось изменение. `--changed` отправляет только эти запросы:

```sh
apix run api --changed                 # то, что ещё не закоммичено
apix run api --changed=origin/main     # то, что эта ветка изменила с момента ответвления от main
```

Запрос запускается снова, когда изменился его собственный файл или его скрипты,
когда изменился `folder.toml` или скрипт папки над ним (каждый запрос этой
папки), когда изменились `apix.toml`, скрипт коллекции, окружение или файл
проекта (каждый запрос) или когда он ссылается на другой изменённый файл
(файл тела, `.proto`). Новые файлы учитываются ещё до коммита; удалённые
запросы перечисляются. Без значения `--changed` сравнивает с базовой веткой
pull request в GitHub Actions (`origin/$GITHUB_BASE_REF`), а в остальных
случаях с `HEAD`. Пишите значение через `=`, чтобы его нельзя было спутать с
папкой для запуска.

```text
2 of 3 requests changed since origin/main
  users/create-user.apix  ← users/create-user.test.js
  users/list-users.apix
```

Как и в pull request, сравнение начинается с места, где ветка отошла от базы,
поэтому то, что тем временем попало в main, не учитывается. Для этого нужна
история: в поверхностном клоне (по умолчанию в `actions/checkout`) `apix`
предупреждает и сравнивает с самой базой; делайте checkout с `fetch-depth: 0`.
Зашифрованные коллекции сравнить нельзя, потому что git видит только их
зашифрованные файлы.

### Что изменилось: `apix diff`

`apix diff` показывает изменение так, как его читает ревьюер: поля запроса,
а не строки TOML, заголовки и параметры query по имени, тело и скрипты
построчно, окружения по переменным. Переформатирование файла не считается
изменением, а запрос, перемещённый или переименованный без других правок, —
это одно перемещение.

```sh
apix diff                       # HEAD против файлов в их текущем виде
apix diff main                  # main против текущего состояния
apix diff v1.2 v1.3 -C api      # между двумя тегами, для коллекции в api/
```

```text
Between main and the working tree: 1 script, 1 request

A  script  users/create-user.test.js
     + pm.test("ok", () => pm.response.to.have.status(200));
M  GET List users  users/list-users.apix
     query._limit: 3 → 5
     headers.Accept: (none) → application/json
```

`--markdown` печатает его для pull request, `--json` — для инструментов, а
`--exit-code` завершается с кодом 1, если что-то изменилось.

### Сводка в pull request

`--markdown report.md` записывает запуск в виде GitHub Markdown: итоги, по
строке на запрос и, раскрытым ниже, что не прошло и почему. Его первая строка —
скрытый маркер с именем коллекции, поэтому шаг CI может найти комментарий,
который он написал в прошлый раз, и отредактировать его вместо добавления
нового.

Action делает всё это. В pull request он отправляет только то, чего касается
pull request, добавляет `apix diff` под сводкой и поддерживает в актуальном
состоянии один комментарий в pull request:

```yaml
on: pull_request
permissions:
  contents: read
  pull-requests: write          # для комментария
jobs:
  api:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0        # история, чтобы найти, где началась ветка
      - uses: 11R5/Apix@main
        with:
          path: api
          changed: "true"       # или коммит, ветка или тег
          diff: "true"
          comment: "true"
```

При push `changed: "true"` сравнивает с коммитом перед push. Сводка также
записывается в `apix-report.md` (вход `markdown`) и показывается на странице
задачи.

В настольном приложении строка состояния показывает ветку и сколько файлов
изменилось с последнего коммита, а боковая панель отмечает изменённые запросы
буквой **M** (изменён) или **A** (новый); см. [руководство пользователя](user-guide.md#git).

### Docker

Для других систем CI есть образ контейнера, в котором только команда `apix`
(публикуется в `ghcr.io/11r5/apix` при создании тега версии; соберите его
сами командой `docker build -t apix .`):

```sh
docker run --rm -v "$PWD:/work" -e APIX_VAR_TOKEN ghcr.io/11r5/apix run api --env staging --junit reports/apix.xml
```

[examples/ci/gitlab-ci.yml](../../examples/ci/gitlab-ci.yml) и
[examples/ci/azure-pipelines.yml](../../examples/ci/azure-pipelines.yml) делают
то же самое в GitLab CI (с образом) и Azure Pipelines (собирая `apix` один раз
и кэшируя его); оба публикуют результаты JUnit.

**Runner** настольного приложения (Ctrl+Shift+R) выполняет те же запуски в
окне; см. [руководство пользователя](user-guide.md#runner).

`apix send <file>` отправляет один запрос и печатает ответ; добавьте `-i` для
заголовков и `--network` для подробностей соединения.

## Наблюдение за API с помощью мониторов

Монитор запускает коллекцию (или её папку или запрос) по расписанию и сообщает
webhook, когда она начинает падать и когда снова проходит. Мониторы
записываются в `apix.toml` коллекции — вручную или через **Вид › Мониторы…**
в приложении (см. [руководство пользователя](user-guide.md#мониторы)):

```toml
[[monitor]]
name = "Health"
every = "5m"
run = "health.apix"
environment = "production"
webhook = "{{alerts_url}}"
```

`apix monitor` выполняет их, пока он запущен, каждый по своему расписанию, и
по ходу перечитывает `apix.toml`, так что правки вступают в силу:

```sh
APIX_VAR_ALERTS_URL=https://hooks.slack.com/… apix monitor api
```

```text
Watching 2 monitor(s) of Shop API; logs in ~/.config/Apix/monitors (Ctrl+C stops)
09:30:05Z ✓ Health                 1 passed · 166 ms
                         next at 09:35:05Z
09:30:05Z ✗ Orders                 1 of 3 failed · 412 ms
    orders/list.apix: got 500 Internal Server Error
    webhook told: failing
```

| Параметр | Что делает |
|---|---|
| `--once` | Запустить каждый монитор один раз и выйти, с кодом 1, если какой-то не прошёл: для cron, планировщика заданий или расписания CI |
| `--list` | Мониторы и их последние результаты |
| `--only NAME` | Только этот монитор (можно повторять); с `--once` он запускается, даже если выключен |
| `--var`, `--env-file` | Переменные поверх окружений мониторов, как в `apix run` (`APIX_VAR_*` тоже читаются) |
| `--log-dir DIR` | Хранить журнал в другом месте (в CI — в кэшируемой папке) |
| `--timeout`, `-k`, `--proxy`, `--cacert` | Транспортные настройки, как для `apix run` |

Журнал хранит последние 500 результатов каждого монитора в `<config>/Apix/monitors`;
настольное приложение читает те же файлы, поэтому показывает то, что нашёл
`apix monitor` на том же компьютере. Webhook получает сообщение только когда
состояние монитора меняется (падение после прохождения или при первом запуске;
прохождение после падения), с телом JSON, которое Slack, Discord, Mattermost и
Google Chat показывают как сообщение.

На сервере запустите `apix monitor api` как службу или поместите
`apix monitor api --once` в cron (`*/5 * * * *`). На GitHub это делает
workflow по расписанию:
[examples/ci/monitors.yml](../../examples/ci/monitors.yml) запускает мониторы
каждые 15 минут через action (`monitor: "true"`) и кэширует журнал, чтобы
восстановления замечались.

## Вход через OAuth 2.0

**Client credentials** (сервис — сервису):

1. Вкладка «Авторизация» › **OAuth 2.0**, тип grant **Client credentials**.
2. Заполните **URL токена**, **Client ID**, **Client secret** и **Scope**.
   Вместо секретов в открытом виде используйте переменные (`{{client_secret}}`,
   отмеченную как секрет).
3. Отправьте. Apix получает токен, затем использует его повторно и обновляет.

**Authorization code с PKCE** (входит пользователь):

1. Зарегистрируйте `http://127.0.0.1:<port>/callback` как адрес
   перенаправления для своего клиента (или оставьте **URL перенаправления**
   пустым, если провайдер принимает любой loopback-порт).
2. Тип grant **Authorization code**, заполните **URL авторизации**,
   **URL токена**, **Client ID** и **Scope**; оставьте отмеченным
   **Использовать PKCE (рекомендуется)**.
3. Нажмите **Получить новый токен** или отправьте запрос. Браузер откроет
   страницу входа; после входа токен появится в Apix.

Настройте OAuth 2.0 один раз для коллекции (правый щелчок › **Авторизация…**),
и каждый запрос, наследующий авторизацию, будет использовать тот же токен.
Токены хранятся в памяти; после перезапуска Apix вход выполняется заново.

## Вызов AWS API

1. Вкладка «Авторизация» › **AWS Signature**.
2. **Ключ доступа** и **Секретный ключ** в виде переменных (`{{aws_access_key}}`,
   `{{aws_secret_key}}`, отмеченные как секрет), **Токен сессии** для временных
   учётных данных, **Регион** (например, `eu-central-1`) и **Сервис** (например,
   `execute-api`, `s3`, `lambda`).
3. Отправьте. Каждый запрос подписывается Signature Version 4 непосредственно
   перед отправкой.

**Копировать как › cURL** пишет `curl --aws-sigv4`, поэтому curl подписывает
запрос заново при запуске; копия для PowerShell содержит подпись, сделанную в
момент копирования и действительную несколько минут.

## Загрузка файла, отправка GraphQL

**Multipart:** Тело › **Multipart**, добавьте поле, переключите его на
**Файл** и выберите файл. Текстовые поля остаются **Текст**. Держите тестовые
файлы внутри коллекции: путь сохраняется относительно запроса, поэтому он
работает на любой машине.

**Двоичные данные:** Тело › **Двоичные данные** отправляет один файл как всё тело.

**GraphQL:** Тело › **GraphQL**, напишите запрос, ниже укажите переменные в виде
JSON. Apix отправляет `{"query": …, "variables": …}` с
`Content-Type: application/json`. Сначала настройте авторизацию, затем нажмите
**Получить схему**: с этого момента редактор запроса подсказывает поля,
аргументы и значения enum, а при наведении показывает их документацию. Схема
хранится для каждого URL, поэтому при следующем открытии запроса она уже на
месте. Чтобы проверить изменение схемы в pull request, сохраните
`apix schema api/graphql.apix > schema.graphql` в репозитории, и diff покажет,
что изменилось.

## Вызов службы gRPC

1. **Запрос › Новый запрос**, затем введите адрес с `grpc://` (или
   `grpcs://` за TLS), например `grpc://localhost:50051`.
2. На вкладке **Сообщение** нажмите **Загрузить методы**. Если рефлексия
   сервера выключена, сначала добавьте файлы `.proto` (**Добавить файл**);
   держите их в коллекции, чтобы пути работали на любой машине.
3. Выберите метод, нажмите **Пример сообщения**, заполните значения.
4. Укажите токен в **Авторизация** (Bearer) или добавьте метаданные в
   **Заголовки**, затем **Отправить**.

В конвейере тот же файл работает с командной строкой:

```sh
apix send api/say-hello.apix --env staging   # код выхода 1, если статус не OK
apix schema api/say-hello.apix > greeter.txt   # что предлагает служба, для сравнения на ревью
```

## Повтор запроса из браузера

1. В инструментах разработчика браузера щёлкните запрос правой кнопкой ›
   **Copy as cURL** (bash или cmd, подходят оба).
2. В Apix щёлкните по полю URL и вставьте. Метод, URL, query, заголовки,
   cookie, авторизация и тело будут заполнены.
3. Отправьте, измените, сохраните.

В обратную сторону: кнопка копирования рядом с **Отправить** даёт запрос в виде
`curl`, `curl.exe` или PowerShell, чтобы вставить его в терминал или отчёт об
ошибке.

## Почему запрос медленный или не проходит

1. Отправьте запрос и откройте вкладку ответа **Сеть**.
2. Полоса времени показывает, уходит ли время на DNS, открытие TCP-соединения,
   рукопожатие TLS, ожидание сервера или загрузку. Медленное TCP-соединение
   указывает на сеть; медленное рукопожатие (по сравнению с TCP, которому нужен
   один круговой обход) — на сервер или лишний круговой обход TLS 1.2.
3. Проверьте удалённый адрес и локальный интерфейс: VPN или прокси видны там.
4. Перенаправления перечислены по порядку. В разделе «Шифрование»: версия TLS,
   набор шифров и то, был ли согласован HTTP/2; цепочка сертификатов показывает
   издателя каждого сертификата и оставшиеся дни, поэтому отсутствующий
   промежуточный сертификат или сертификат, срок которого скоро истекает,
   сразу заметны. Для сжатого тела видно, сколько сэкономлено.

Тот же отчёт доступен в терминале:

```sh
apix send my-api/health.apix --network
```

## Как дать ИИ-агенту работать с коллекцией (MCP)

`apix mcp` предоставляет коллекцию по Model Context Protocol, чтобы ИИ-агент
(Claude, помощник редактора, любой клиент MCP) мог работать с вашим API так же,
как вы в Apix. Он говорит на MCP через стандартный ввод и вывод; агент сам его
запускает. С Claude Code:

```bash
claude mcp add my-api -- apix mcp /path/to/my-api
```

Другие клиенты принимают ту же команду в своей конфигурации, например:

```json
{ "mcpServers": { "my-api": { "command": "apix", "args": ["mcp", "/path/to/my-api"] } } }
```

Агент получает четыре инструмента:

| Инструмент | Что делает |
|---|---|
| `list_requests` | запросы (путь, метод, имя, URL с `{{variables}}`) всей коллекции или папки |
| `list_environments` | окружения и имена их переменных, но никогда не значения |
| `send_request` | отправляет один запрос с его скриптами и тестами, в окружении, с переменными, которые задаёт агент; возвращает статус, время, заголовки, тело (до 64 KB) и результаты тестов |
| `run_requests` | запускает папку или всю коллекцию с её тестами и сообщает, что прошло |

Доступны только запросы внутри этой коллекции. `--list-only` оставляет два
инструмента для перечисления и убирает те, что отправляют запросы. Секреты
остаются на месте: агент может попросить отправить запрос с токеном, но ему
никогда не показывают значение токена (ответ, который повторяет токен, — другое
дело, поэтому следите, что вы разрешаете агенту отправлять). Для
зашифрованной коллекции передайте пароль в `APIX_PASSWORD`.
