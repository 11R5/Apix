## إرسال طلبك الأول وحفظه

1. **ملف › مجموعة جديدة…**، اختر مجلدًا فارغًا وأعطها اسمًا.
2. يفتح Ctrl+N طلب GET جديدًا. اكتب `https://jsonplaceholder.typicode.com/users`.
3. يرسله Ctrl+Enter؛ وتظهر الاستجابة على اليمين.
4. يحفظه Ctrl+S كملف جديد في مجلد المجموعة. انقر عليه بزر الفأرة الأيمن في
   الشريط الجانبي › **إعادة تسمية** لتعطيه اسمًا مثل "List users".

الملف نص TOML عادي يمكنك قراءته وتعديله:

```toml
name = "List users"
url = "https://jsonplaceholder.typicode.com/users"
```

## الاحتفاظ بمجموعة في git

المجموعة مجلد:

```
my-api/
├── apix.toml                اسم المجموعة، المتغيرات، المصادقة المشتركة
├── environments/
│   ├── staging.toml         القيم المشتركة
│   └── staging.local.toml   القيم السرية (يتجاهلها git)
├── users/
│   ├── folder.toml          اختياري: المصادقة لطلبات هذا المجلد
│   ├── list-users.apix
│   └── create-user.apix
└── health.apix
```

أودِع كل شيء عدا `*.local.toml`؛ يضيف Apix هذا النمط إلى `.gitignore` بنفسه
أول مرة يكتب فيها سرًّا. كل طلب ملف صغير مستقل، فتبقى المراجعات والدمج سهلة
القراءة.

## العمل مع dev وstaging وproduction

1. افتح **البيئة › المتغيرات والبيئات…** (Ctrl+E).
2. أضف بيئات باسم `dev` و`staging` و`prod`، لكل منها `base_url`.
3. استخدم `{{base_url}}/users` في طلباتك.
4. اختر البيئة في الشريط الجانبي، تحت اسم المجموعة.

القيم التي يجب ألا تُودَع (الرموز المميزة، كلمات المرور) تحصل على علامة **سري**.
يحتفظ كل عضو في الفريق بملف `*.local.toml` الخاص به. المتغير المعرَّف على مستوى
المجموعة قيمة افتراضية يمكن للبيئات تجاوزها.

## مشاركة مجموعة تحتوي على أسرار

حين تكون المجموعة كلها حساسة (روابط داخلية، بيانات عملاء نموذجية، مفاتيح
طويلة الأمد)، شفّرها:

1. **ملف › تشفير هذه المجموعة…** واختر كلمة مرور.
2. احفظ **مفتاح الاسترداد** الذي يُعرض لك في مدير كلمات المرور.
3. أودِع المجلد. على القرص يكون مجموعة من الكائنات المشفّرة؛ حتى أسماء الملفات
   مخفية.

يفتح أعضاء الفريق المجلد في Apix ويكتبون كلمة المرور. في الطرفية أو في CI:

```sh
APIX_PASSWORD='…' apix run my-api --env staging
```

يكتب `apix decrypt my-api --out my-api-plain` نسخة غير مشفّرة، ومع
`--recovery` يستخدم مفتاح الاسترداد بدل كلمة المرور.

## الانتقال من Postman

1. في Postman، صدّر المجموعة (Collection v2.1) وكل بيئة.
2. في Apix، **ملف › استيراد…** أو أفلت الملفات على النافذة.
   أو في الطرفية:

   ```sh
   apix import "My API.postman_collection.json"            # ينشئ ./my-api
   apix import "Staging.postman_environment.json" --into my-api
   ```

3. اقرأ تقرير الاستيراد: كل ما تعذّر نقله مذكور فيه
   (مثل مصادقة NTLM أو الاستجابات الأمثلة المحفوظة).
4. تُحفظ سكربتات ما قبل الطلب والاختبارات كملفات `.js` بجوار طلباتها؛
   ولا يشغّلها Apix بعد.
5. لـ OAuth 2.0 بمنح رمز التفويض، سجّل رابط إعادة توجيه loopback
   مثل `http://127.0.0.1:8765/callback` لدى مزوّد الهوية
   واضبطه في تبويب **المصادقة**.

تنقل مساحة عمل كاملة؟ استخدم **Settings › Data › Export data** في Postman،
ثم افتح المجلد (أو ملف zip) في Apix أو أفلته عليه: تنتقل كل مجموعة
وبيئة ومتغير عام كمشروع واحد
(ويفعل `apix import postman-export.zip` الشيء نفسه). أعضاء الفريق الذين يبقون على
Postman يستعيدون مجموعتك عبر **تصدير إلى Postman…**.

## تشغيل مجموعة في CI

يرسل `apix run` كل طلبات المجموعة بترتيب الشريط الجانبي ويخرج
برمز غير صفري إذا فشل أي منها، فيصلح خطوةً في CI:

```sh
apix run my-api --env staging --var token="$API_TOKEN"
```

الطلبات التي لها اختبارات (سكربتات أو **الفحوص**) تنجح أو تفشل باختباراتها؛
والبقية برمز حالتها. تسرد المخرجات كل اختبار تحت طلبه:

```text
create.apix                              201 Created  466.7 ms · 42 B
  │ new id 101
  ✓ created
get.apix                                 200 OK  174.7 ms · 292 B
  ✓ status 200
  ✗ has the right id expected 1 to equal 2

1 passed, 1 failed (1 failed tests)
```

ما يضبطه سكربت (`pm.environment.set`، `pm.variables.set`) ينتقل إلى
الطلبات التالية في التشغيل، و`pm.execution.setNextRequest("name")`
يقفز إلى طلب آخر (`null` ينهي التكرار).

الخيارات:

| الخيار | ما يفعله |
|---|---|
| `apix run my-api/users` | الطلبات في مجلد فقط (أو ملف طلب واحد) |
| `-d, --data users.csv` | تشغيل مدفوع بالبيانات: كل صف CSV أو JSON تكرار واحد، وأعمدته متغيرات (`{{email}}`، `pm.iterationData.get("email")`) |
| `-n, --iterations 5` | المرور على الطلبات 5 مرات (الافتراضي: مرة لكل صف بيانات، وإلا فمرة واحدة) |
| `--delay 200` | الانتظار 200 ms بين الطلبات |
| `--bail` | التوقف عند أول طلب يفشل |
| `-p, --parallel 4` | تشغيل 4 تكرارات معًا، كأنهم 4 مستخدمين؛ كل منها يرسل طلباته بالترتيب ويحتفظ لنفسه بما تضبطه سكربتاته |
| `--junit report.xml` | تقرير JUnit XML، تعرضه خدمات CI كقائمة اختبارات |
| `--json report.json` / `--html report.html` | كل شيء بصيغة JSON، أو صفحة تُفتح في أي متصفح |
| `--markdown report.md` | ملخص لتعليق على طلب دمج أو لملخص مهمة CI (انظر أدناه) |
| `--changed` / `--changed=origin/main` | الطلبات التي يمسّها تغيير فقط (انظر أدناه) |
| `--timeout 10`، `-k`، `--proxy URL` | تجاوز إعدادات النقل الخاصة بالطلبات |
| `--env-file .env` | متغيرات من ملف dotenv (انظر أدناه) |

يبدو ملف البيانات هكذا؛ والقيم الآتية من خارج المجموعة (`--var` والمذكورة
أدناه) تتقدّم على أعمدته:

```csv
id,name
1,Leanne Graham
2,Ervin Howell
```

### الأسرار في CI

تبقى الأسرار خارج git (ملفات `.local.toml` متجاهَلة، وسلسلة المفاتيح على
حاسوبك)، لذا يسلّمها خط CI بإحدى ثلاث طرق، كل منها
تتقدّم على التي قبلها:

1. `--env-file .env`: ملف dotenv من أسطر `NAME=value` (يُسمح بتعليقات `#`
   وعلامات الاقتباس و`export`).
2. متغيرات البيئة `APIX_VAR_<NAME>`: ‏`APIX_VAR_TOKEN` يملأ
   `{{token}}`. تُكتب أسرار CI عادةً بأحرف كبيرة، لذا يطابق الاسمُ
   متغيرًا تعرّفه المجموعة أو تستخدمه طلباتها أيًّا كانت حالة أحرفه.
3. `--var name=value`.

تتقدّم الطرق الثلاث كلها على قيم البيئة (وعلى أعمدة ملف البيانات).
يطبع `apix` على stderr الأسماء التي أخذها ومن أين، ولا يطبع
القيم أبدًا.

```sh
APIX_VAR_TOKEN="$API_TOKEN" apix run api --env staging
```

### GitHub Actions

المستودع هو أيضًا GitHub Action. يشغّل المجموعة ويكتب تقارير
JUnit وHTML. عند استخدامه بوسم إصدار، ينزّل `apix` الخاص بذلك الإصدار
(ثوانٍ)؛ وعند فرع أو إيداع يبني `apix` أول مرة ويخزّنه مؤقتًا،
و`apix-version: latest` (أو `0.1.1`) ينزّل إصدارًا بدلًا من ذلك:

```yaml
- uses: 11R5/Apix@v0.1.1        # إصدار: يُنزَّل apix ولا يُبنى
  with:
    path: api
    environment: staging        # أيضًا: data, iterations, delay, bail, env-file, junit, html, json, markdown, changed, diff, comment, args, apix-version
  env:
    APIX_VAR_TOKEN: ${{ secrets.API_TOKEN }}
```

[examples/ci/github-actions.yml](../../examples/ci/github-actions.yml) سير عمل
كامل: يشغّل المجموعة مرة لكل بيئة (مصفوفة من
`test` و`staging`)، ويعرض نتائج JUnit في صفحة التشغيل ويحتفظ
بتقارير HTML. ويضيف الإجراء أيضًا ملخصه بصيغة Markdown إلى صفحة المهمة.

## ما تغير فقط: تشغيلات تعرف git

المجموعة مجلد في git، لذا يستطيع `apix` أن يسأل git عمّا مسّه
تغيير ما. يرسل `--changed` تلك الطلبات فقط:

```sh
apix run api --changed                 # ما لم يُودَع بعد
apix run api --changed=origin/main     # ما غيّره هذا الفرع منذ تفرّعه عن main
```

يُعاد تشغيل الطلب حين يتغير ملفه أو سكربتاته، أو حين يتغير
`folder.toml` أو سكربت مجلد فوقه (كل طلب في ذلك
المجلد)، أو حين يتغير `apix.toml` أو سكربت المجموعة أو بيئة أو
ملف المشروع (كل طلب)، أو حين يسمّي ملفًا آخر متغيرًا
(ملف متن، ملف `.proto`). تُحتسب الملفات الجديدة قبل إيداعها؛
وتُسرد الطلبات المحذوفة. دون قيمة، يقارن `--changed` مع
الفرع الأساسي لطلب الدمج على GitHub Actions (`origin/$GITHUB_BASE_REF`)
ومع `HEAD` في غير ذلك. اكتب القيمة مع `=`، كي لا تُفهم خطأً
على أنها المجلد المراد تشغيله.

```text
2 of 3 requests changed since origin/main
  users/create-user.apix  ← users/create-user.test.js
  users/list-users.apix
```

كما في طلب الدمج، تبدأ المقارنة من حيث تفرّع الفرع عن الأساس،
فما وصل إلى main في الأثناء لا يُحتسب. وهذا يحتاج إلى السجل: في
نسخة ضحلة (الافتراضي في `actions/checkout`) يحذّر `apix` ويقارن
مع الأساس نفسه؛ استخدم `fetch-depth: 0` عند السحب. لا يمكن مقارنة المجموعات
المشفّرة، لأن git لا يرى إلا ملفاتها المشفّرة.

### ما الذي تغير: `apix diff`

يعرض `apix diff` التغيير كما يقرؤه المراجع: حقول الطلب
بدل أسطر TOML، والترويسات ومعاملات الاستعلام بالاسم، والمتن
والسكربتات سطرًا سطرًا، والبيئات حسب المتغير. إعادة تنسيق ملف
ليست تغييرًا، والطلب الذي نُقل أو أُعيدت تسميته دون تعديلات أخرى يُعد
نقلًا واحدًا.

```sh
apix diff                       # HEAD مقابل الملفات كما هي الآن
apix diff main                  # main مقابل الآن
apix diff v1.2 v1.3 -C api      # بين وسمين، للمجموعة في api/
```

```text
Between main and the working tree: 1 script, 1 request

A  script  users/create-user.test.js
     + pm.test("ok", () => pm.response.to.have.status(200));
M  GET List users  users/list-users.apix
     query._limit: 3 → 5
     headers.Accept: (none) → application/json
```

يطبعه `--markdown` لطلب دمج، و`--json` للأدوات، و
`--exit-code` يخرج بالرمز 1 حين يتغير شيء.

### ملخص على طلب الدمج

يكتب `--markdown report.md` التشغيل بصيغة GitHub Markdown: المجاميع، وصفًا
لكل طلب، وتحتها مفتوحًا ما فشل ولماذا. سطره الأول
علامة مخفية فيها اسم المجموعة، فتستطيع خطوة CI أن تجد التعليق
الذي كتبته في المرة السابقة وتعدّله بدل إضافة تعليق آخر.

الإجراء يفعل كل هذا. في طلب الدمج يرسل فقط ما يمسّه طلب
الدمج، ويضيف `apix diff` تحت الملخص، ويُبقي تعليقًا واحدًا على
طلب الدمج محدَّثًا:

```yaml
on: pull_request
permissions:
  contents: read
  pull-requests: write          # من أجل التعليق
jobs:
  api:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0        # السجل، لمعرفة أين بدأ الفرع
      - uses: 11R5/Apix@main
        with:
          path: api
          changed: "true"       # أو إيداع أو فرع أو وسم
          diff: "true"
          comment: "true"
```

عند الدفع (push)، يقارن `changed: "true"` مع الإيداع الذي سبق الدفع.
يُكتب الملخص أيضًا إلى `apix-report.md` (المُدخل `markdown`) ويُعرض في
صفحة المهمة.

في تطبيق سطح المكتب يعرض شريط الحالة الفرع وعدد الملفات التي
تغيرت منذ آخر إيداع، ويُعلّم الشريط الجانبي الطلبات المتغيرة بـ
**M** (متغير) أو **A** (جديد)؛ انظر [دليل المستخدم](user-guide.md#git).

### Docker

لأنظمة CI الأخرى توجد صورة حاوية فيها الأمر `apix` وحده
(تُنشر على `ghcr.io/11r5/apix` عند وسم إصدار؛ ابنها بنفسك
بـ `docker build -t apix .`):

```sh
docker run --rm -v "$PWD:/work" -e APIX_VAR_TOKEN ghcr.io/11r5/apix run api --env staging --junit reports/apix.xml
```

يفعل [examples/ci/gitlab-ci.yml](../../examples/ci/gitlab-ci.yml) و
[examples/ci/azure-pipelines.yml](../../examples/ci/azure-pipelines.yml)
الشيء نفسه في GitLab CI (مع الصورة) وAzure Pipelines (ببناء `apix`
مرة واحدة وتخزينه مؤقتًا)؛ وكلاهما ينشر نتائج JUnit.

يجري **Runner** في تطبيق سطح المكتب (Ctrl+Shift+R) التشغيلات نفسها في نافذة؛
انظر [دليل المستخدم](user-guide.md#runner).

يرسل `apix send <file>` طلبًا واحدًا ويطبع الاستجابة؛ أضف `-i` للترويسات
و`--network` لتفاصيل الاتصال.

## مراقبة API بشكل مجدول

المراقِب يشغّل مجموعة (أو مجلدًا أو طلبًا منها) وفق جدول زمني
ويُبلغ webhook حين تبدأ بالفشل وحين تنجح مجددًا. تُكتب المراقِبات
في ملف `apix.toml` الخاص بالمجموعة، يدويًا أو من **عرض › المراقِبات…**
في التطبيق (انظر [دليل المستخدم](user-guide.md#المراقبات)):

```toml
[[monitor]]
name = "Health"
every = "5m"
run = "health.apix"
environment = "production"
webhook = "{{alerts_url}}"
```

يشغّلها `apix monitor` ما دام يعمل، كلًّا وفق جدوله،
ويعيد قراءة `apix.toml` أثناء عمله، فتسري التعديلات:

```sh
APIX_VAR_ALERTS_URL=https://hooks.slack.com/… apix monitor api
```

```text
Watching 2 monitor(s) of Shop API; logs in ~/.config/Apix/monitors (Ctrl+C stops)
09:30:05Z ✓ Health                 1 passed · 166 ms
                         next at 09:35:05Z
09:30:05Z ✗ Orders                 1 of 3 failed · 412 ms
    orders/list.apix: got 500 Internal Server Error
    webhook told: failing
```

| الخيار | ما يفعله |
|---|---|
| `--once` | تشغيل كل مراقِب مرة واحدة ثم الخروج، بالرمز 1 حين يفشل أحدها: لـ cron أو Task Scheduler أو جدول CI |
| `--list` | المراقِبات وآخر نتائجها |
| `--only NAME` | هذا المراقِب فقط (يمكن تكراره)؛ ومع `--once` يعمل حتى لو كان معطّلًا |
| `--var`، `--env-file` | متغيرات تتقدّم على بيئات المراقِبات، كما في `apix run` (وتُقرأ `APIX_VAR_*` أيضًا) |
| `--log-dir DIR` | حفظ السجل في مكان آخر (في CI، مجلد مخزّن مؤقتًا) |
| `--timeout`، `-k`، `--proxy`، `--cacert` | إعدادات النقل، كما في `apix run` |

يحفظ السجل آخر 500 نتيجة لكل مراقِب في `<config>/Apix/monitors`؛
ويقرأ تطبيق سطح المكتب الملفات نفسها، فيعرض ما وجده `apix monitor`
على الحاسوب نفسه. لا يُبلَّغ الـ webhook إلا حين تتغير حالة المراقِب
(الفشل بعد النجاح، أو في أول تشغيل؛ النجاح بعد الفشل)، بمتن
JSON يعرضه Slack وDiscord وMattermost وGoogle Chat كرسالة.

على خادم، شغّل `apix monitor api` كخدمة، أو ضع
`apix monitor api --once` في cron ‏(`*/5 * * * *`). على GitHub، يتولّى ذلك
سير عمل مجدول:
يشغّل [examples/ci/monitors.yml](../../examples/ci/monitors.yml) المراقِبات
كل 15 دقيقة عبر الإجراء (`monitor: "true"`) ويخزّن السجل مؤقتًا كي
يُلاحَظ التعافي.

## تسجيل الدخول عبر OAuth 2.0

**بيانات اعتماد العميل** (من خدمة إلى خدمة):

1. تبويب **المصادقة** › **OAuth 2.0**، ونوع المنح **بيانات اعتماد العميل**.
2. املأ **عنوان URL للرمز المميز** و**معرّف العميل** و**سر العميل** و**النطاق**. استخدم
   المتغيرات (`{{client_secret}}`، معلَّمًا كسري) بدل كتابة الأسرار حرفيًا.
3. أرسل. يجلب Apix رمزًا مميزًا، ثم يعيد استخدامه ويجدّده.

**رمز التفويض مع PKCE** (يسجّل مستخدم دخوله):

1. سجّل `http://127.0.0.1:<port>/callback` كرابط إعادة توجيه لعميلك
   (أو اترك **عنوان URL لإعادة التوجيه** فارغًا إن كان المزوّد يقبل أي منفذ loopback).
2. نوع المنح **رمز التفويض**، واملأ **عنوان URL للتفويض** و**عنوان URL للرمز المميز**
   و**معرّف العميل** و**النطاق**؛ وأبقِ **استخدام PKCE (موصى به)** محدّدًا.
3. اضغط **الحصول على رمز جديد** أو أرسل. يفتح متصفحك صفحة تسجيل الدخول؛ وبعد
   أن تسجّل دخولك، يظهر الرمز المميز في Apix.

اضبط OAuth 2.0 مرة واحدة على المجموعة (نقرة بالزر الأيمن › **المصادقة…**) وسيستخدم كل طلب
يرث المصادقة الرمز المميز نفسه. تبقى الرموز المميزة في الذاكرة؛ وإعادة تشغيل Apix
تعني تسجيل الدخول من جديد.

## استدعاء API من AWS

1. تبويب **المصادقة** › **AWS Signature**.
2. **مفتاح الوصول** و**المفتاح السري** كمتغيرات (`{{aws_access_key}}`،
   `{{aws_secret_key}}` معلَّمَين كسريّين)، و**رمز الجلسة** لبيانات الاعتماد
   المؤقتة، و**المنطقة** (مثلًا `eu-central-1`) و**الخدمة** (مثلًا
   `execute-api` أو `s3` أو `lambda`).
3. أرسل. يُوقَّع كل طلب بـ Signature Version 4 قبيل خروجه مباشرة.

**نسخ كـ › cURL** يكتب `curl --aws-sigv4`، فيوقّعه curl من جديد حين
تشغّله؛ أما نسخة PowerShell فتحتوي على توقيع صُنع لحظة النسخ، صالح
لبضع دقائق.

## رفع ملف وإرسال GraphQL

**Multipart:** ‏**المتن** › **Multipart**، أضف حقلًا، وحوّله إلى **ملف** واختر
الملف. تبقى الحقول النصية **نص**. احتفظ بملفات الاختبار داخل المجموعة: يُحفظ
المسار نسبةً إلى الطلب، فيعمل على كل جهاز.

**ثنائي:** ‏**المتن** › **ثنائي** يرسل ملفًا واحدًا كمتن كامل.

**GraphQL:** ‏**المتن** › **GraphQL**، اكتب الاستعلام، وضع المتغيرات بصيغة JSON تحته.
يرسل Apix ‏`{"query": …, "variables": …}` مع `Content-Type: application/json`.
اضبط المصادقة أولًا، ثم اضغط **جلب المخطط**: من حينها يقترح محرر الاستعلام
الحقول والوسائط وقيم enum، ويعرض التمرير فوقها
توثيقها. يُحفظ المخطط لكل رابط، فيكون موجودًا أصلًا حين تفتح الطلب
في المرة التالية. للتحقق من تغيير في المخطط ضمن طلب دمج، احفظ
`apix schema api/graphql.apix > schema.graphql` في المستودع ودع
الفرق يُظهر ما تغير.

## استدعاء خدمة gRPC

1. **الطلب › طلب جديد**، ثم اكتب العنوان مع `grpc://` (أو
   `grpcs://` خلف TLS)، مثلًا `grpc://localhost:50051`.
2. في تبويب **الرسالة** اضغط **تحميل الطرق**. إن كان انعكاس الخادم
   معطّلًا، أضف ملفات `.proto` أولًا (**إضافة ملف**)؛ واحتفظ بها في
   المجموعة كي تعمل المسارات على كل جهاز.
3. اختر الطريقة، واضغط **رسالة مثال**، واملأ القيم.
4. اضبط الرمز المميز في **المصادقة** (Bearer) أو أضف بيانات وصفية في **الترويسات**، ثم
   **إرسال**.

في خط CI، يعمل الملف نفسه مع سطر الأوامر:

```sh
apix send api/say-hello.apix --env staging   # رمز الخروج 1 ما لم تكن الحالة OK
apix schema api/say-hello.apix > greeter.txt   # ما تقدّمه الخدمة، لمقارنته في المراجعات
```

## إعادة إنتاج طلب من المتصفح

1. في أدوات المطوّر في المتصفح، انقر بالزر الأيمن على طلب › **Copy as cURL**
   (bash أو cmd، كلاهما يعمل).
2. في Apix، انقر حقل الرابط والصق. تُملأ الطريقة والرابط والاستعلام والترويسات وملفات تعريف الارتباط
   والمصادقة والمتن.
3. أرسل، عدّل، احفظ.

وفي الاتجاه المعاكس، يعطيك زر النسخ بجوار **إرسال** الطلبَ بصيغة
`curl` أو `curl.exe` أو PowerShell لتلصقه في طرفية أو في تقرير خطأ.

## معرفة سبب بطء طلب أو فشله

1. أرسل الطلب وافتح تبويب **الشبكة** في الاستجابة.
2. يُظهر شريط التوقيت هل يذهب الوقت إلى DNS، أم فتح اتصال
   TCP، أم مصافحة TLS، أم انتظار الخادم، أم التنزيل. اتصال
   TCP البطيء يشير إلى الشبكة؛ والمصافحة البطيئة (مقارنة بـ
   TCP، الذي يستغرق رحلة ذهاب وإياب واحدة) تشير إلى الخادم أو إلى رحلة الذهاب والإياب الإضافية في TLS 1.2.
3. افحص العنوان البعيد والواجهة المحلية: تظهر هناك شبكة VPN أو
   وكيل.
4. تُسرد عمليات إعادة التوجيه بالترتيب. تحت **التشفير**: إصدار TLS ومجموعة
   التشفير وهل اتُّفق على HTTP/2؛ وتُظهر سلسلة الشهادات مُصدِر كل
   شهادة والأيام المتبقية لها، فتبرز الشهادة الوسيطة المفقودة أو القريبة
   من الانتهاء. ويُظهر المتن المضغوط مقدار ما وفّره.

التقرير نفسه متاح في الطرفية:

```sh
apix send my-api/health.apix --network
```

## السماح لوكيل ذكاء اصطناعي باستخدام مجموعتك (MCP)

يقدّم `apix mcp` مجموعةً عبر Model Context Protocol، فيستطيع وكيل ذكاء
اصطناعي (Claude، أو مساعد محرر شيفرة، أو أي عميل MCP) العمل مع الـ API الخاص بك
كما تعمل أنت في Apix. يتحدث بروتوكول MCP عبر الإدخال والإخراج القياسيين؛ ويشغّله
الوكيل. مع Claude Code:

```bash
claude mcp add my-api -- apix mcp /path/to/my-api
```

تأخذ العملاء الأخرى الأمر نفسه في إعداداتها، مثلًا:

```json
{ "mcpServers": { "my-api": { "command": "apix", "args": ["mcp", "/path/to/my-api"] } } }
```

يحصل الوكيل على أربع أدوات:

| الأداة | ما تفعله |
|---|---|
| `list_requests` | الطلبات (المسار، الطريقة، الاسم، الرابط مع `{{variables}}`)، للمجموعة كلها أو لمجلد |
| `list_environments` | البيئات وأسماء متغيراتها، ولا تُعرض القيم أبدًا |
| `send_request` | يرسل طلبًا واحدًا مع سكربتاته واختباراته، في بيئة، مع متغيرات يضبطها الوكيل؛ ويعيد الحالة والوقت والترويسات والمتن (حتى 64 KB) ونتائج الاختبارات |
| `run_requests` | يشغّل مجلدًا أو المجموعة كلها مع اختباراتها ويذكر ما نجح |

لا يمكن الوصول إلا إلى الطلبات داخل تلك المجموعة. يُبقي `--list-only`
أداتي السرد ويُسقط الأدوات التي ترسل. تبقى الأسرار في مكانها:
يستطيع الوكيل أن يطلب إرسال طلب برمز مميز، لكنه لا يُعرض عليه أبدًا
قيمة الرمز (الاستجابة التي تعيده أمر آخر، فانتبه لما
تسمح للوكيل بإرساله). للمجموعة المشفّرة، أعطِ كلمة المرور في
`APIX_PASSWORD`.
